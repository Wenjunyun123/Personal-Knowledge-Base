朋友经常喊我帮忙看一下他做的项目怎么样，帮着提点意见，就看一眼的事，还挺折腾。

那边要么先把项目部署上线，要么把代码推到 Git，我这边再拉下来跑起来才能看。

虽折腾但不好意思拒绝，以前自己的 Agent 账号额度不够用的时候，经常会借他的来用。

我们一个用 Claude Code，一个用 Codex，正好可以互相借用对比结果。

但每次登录别人账号，总有点害怕被封号。直到最近，我们找到了一个多 Agent 协作工具。

在一个房间里，能够实时看到各自对项目的改动，还能互相使用对方的 Agent。

这工具就叫 **Tutti** **VM**，上个月在介绍完他们的开源版后，便一直关注着。

下载地址：https://tutti.sh/?2fq

![[笔记同步助手/images/4c37583eb43101a6bc3c9787ebe04b2a_MD5.png]]

此前开源版，解决了一个人的 Claude Code 和 Codex 之间共享上下文，接力干活。

而这次他们的 VM 版本，则是把开源版本的一个人扩展到了多人、多 Agent 的实时协作。

打开工具，连上自己的 Agent，然后创建一个房间，便可邀请朋友一起加入进来。

![[笔记同步助手/images/d73a2f5c3beb653befbd1ec559da1c15_MD5.png]]

这个房间就像一个一直存在的云端共享工作区，所有的 Agent 对话内容和产物都留在这里。

我们可以一起实时并行协作开发项目，也能自由使用房间里共享的 Agent。

目前产品还在内测，创建房间需要邀请码，但加入房间不用，邀请码的获取方式后面会说。

![[笔记同步助手/images/4b515ad03ad7c43988618e5d87a2011d_MD5.png]]

那它是怎么做到的？一开始我没想明白，后来我特意去翻看了一下他们的技术解读。

下面看效果的同时，顺便按我的理解，说说它的实现原理，还挺有意思的。

### 账号在本地，干活在云上

先看个效果。比如我在 Tutti VM 上，让它帮我部署启动 DeepSeek Harness 项目。

Agent 拉回来的代码会直接存在云端，部署运行后，房间其他伙伴，打开浏览器也能访问。

![[笔记同步助手/images/6568dcd34731d68389764293640758fe_MD5.png]]

看着都是在自己的电脑上操作，但实际房间里大家所干的活都能在 Agent 看板上看到。

包括工作中、已完成、失败、已停止的任务，还有对话的详情以及产物，看得一清二楚。

![[笔记同步助手/images/b702be656ab1d5365e51e1902b7a425f_MD5.png]]

整个登录状态并没离开过我的电脑，但所干的活却像在同一台云端电脑里，怎么做到的？

本地和云端的优点，向来不可兼得，Tutti VM 的解法，是把**身份、执行、共享**三件事拆开，各放各的位置。

跟账号有关的东西，比如登录状态、凭据、API key 这些敏感信息，留在本地机子上，云端从头到尾拿不到。

Agent 干活的地方，则挪进一个受管的本地虚拟机，进程调用、文件读写在这一层被接管，每条指令该去物理机、虚拟机还是云端，由它来分发。

而云端则是作为共享和协作工作区，运行的环境、对话上下文，以及产出的代码、图片、视频等，全都存在这里。

这些内容从产出的那一刻起，就已经存在云端，不用我们主动走上传下载这种传统方式。

![[笔记同步助手/images/fa148b61c58d52a081acbff6f940cc8b_MD5.png]]

就像一台一直开着的共享电脑，它不属于任何一个人或 Agent，谁都能在这台机子上干活。

而且这台电脑上只有一份状态，项目的文件、依赖、跑着的服务，大家看到的都是同一份最新的。

人和 Agent 随时可以进出，房间一直都在，环境配置一次就行，后面进来的人能直接干活。

官方管这叫「组织持久化共享工作区」，在我看来，更像是给项目安了个家，人来人往，资产都留在家里。

另外 Tutti VM 里面的功能**「借用 Agent」** ，也是基于这套思路顺出来的能力。

当在房间群聊里，将自己的 Agent 开启共享，其他成员就可以在房间里使用我的额度。

![[笔记同步助手/images/81a3826074db310ff636cd8555ad1f05_MD5.png]]

这样当朋友的额度用完了，还可以接着用我的继续干活，还能引用房间里的对话和文件。

但需要注意，借的是能力，不是账号，登录状态没有转手，他随时可以取消共享。

![[笔记同步助手/images/776c286235a97bbb8997991fbbf8dadc_MD5.png]]

回想开篇提到的封号顾虑，这种不碰对方账号密码的方式，自然也不存在什么风险。

### 同时开工，互不打架

再看一个更厉害的功能。我和朋友各自同时让 Agent 改同一个项目，他改他的，我改我的。

我让 Codex 帮忙将页面上的背景改为浅色，而朋友那边将页面标题改为文件转换神器。

![[笔记同步助手/images/619ce39dfddc748d7ff34189ac4369ac_MD5.jpg]]

可以看到，两边各自 Agent 都对同个项目页面进行改动，没有任何代码冲突。

多个不同厂商的 Agent，在同一个项目里同时动手，为什么没有产生冲突？

这场景类似多人同时编辑同一个文档，像 Google Docs、Figma 早就给出了解决方案。

解法的原理不难理解，人在编辑文档的时候，翻来覆去就插入、删除、改格式这几种操作。

当两种操作撞在一起怎么办，在应用里提前写好规则，行业里常见的算法有 OT 和 CRDT。

但轮到多 Agent 协同，这套解法并不适合。

Agent 在干活的时候，开终端、装依赖、跑脚本、增删文件，动作种类根本数不过来。

比如我们俩的 Agent 同时装 npm 依赖，node\_modules 可能直接被装坏。

又比如一个 Agent 正往文件里写内容，另一个恰好把这个文件移走了。

这些状况想提前写规则，根本写不完。

Tutti VM 自研一套 Agent 协同技术，把实时协作下沉到文件系统层而不是应用层。

道理很简单，不管是 Claude Code、Codex、vim，还是十年前的一段 Shell 脚本。

谁也不会为了协作去改自己的代码，但它们干任何活，最后都要落到读文件、写文件上。

把冲突处理做进文件这层地基，上面站着的工具一行代码不用改，天然就有了协同能力。

同样是协同引擎，Google Docs 管住的是一个文档，Tutti VM 管的是整个项目的文件系统。

### 真正价值，不止于协作

拆完原理退一步看，这套架构真正动的，是 Agent 协作的时序。

现在主流的多 Agent 产品，一个任务开一个沙箱，Agent 被关在各自的多元宇宙里。

冲突和分歧留到事后，靠总结、交接、git 合并来收拾。

任务并发是上去了，但离一次真正的并行协作，还差着一层。

当 Agent 的数量越多，花在总结和交接上的时间也就越多。

这大概也是不少团队的感受，Agent 干活明明快了，整个组织的效率却没快多少。

Tutti VM 做的事说到底就一句，把共享和协调从事后挪到事中。

官方还透露了 SDK 和企业私有化部署的计划，往后团队的本地 Agent 可以直接接入这套能力。

### 写在最后

2010 年代，Google Docs 把多人同时编辑一个文档，变成了理所当然的事。

在我看来，Tutti VM 赌的是同一件事在 Agent 时代重演，对象从一个文档，换成了整个工作现场。

这两年 Agent 从聊天助手走到项目执行者，一个人同时用两三个 Agent 已经不算新鲜。

下一步要解决的，就是它们之间怎么协作，靠消息转述撑不了多久，共享工作现场早晚会成为这类工具的标配。

这条路上 Tutti VM 未必是终点，但把协同做进文件系统这一步，方向我认。
