## 核心观点：真正的问题是信任，而不是生产力

Lauren Tan 认为，软件工程师在 Agent 时代面临的核心问题不是如何让 Agent 写出更多代码，而是如何在生产力大幅提升的同时，保持甚至提高代码质量。盲目信任 Agent 并不可靠，更有效的做法是投入时间构建一个可信的 Agent 环境，让 Agent 的默认行为受到代码、工具和验证机制的约束。

她曾花约六个月时间，才达到可以向生产环境提交数千个 Pull Request（PR）的程度，其中许多任务甚至在她睡觉时完成。目标不是简单地把所有工作自动化，而是建立一套能够持续产生高质量代码的外部反馈循环。

## 从低信任环境走向高信任环境

构建高信任 Agent 环境可以分为三层。越靠下的层次越确定、越可复现，也越应该优先建设。

-   **代码与 API 设计：**通过良好的 API、清晰的架构边界和合适的模块结构，让正确用法成为最自然的用法。
-   **Lint、类型系统、编译器与测试：**使用确定性规则限制 Agent 的行为，自动阻止反模式进入代码库。
-   **运行时验证与形式化验证：**让 Agent 自行运行代码、调用调试工具、生成截图或证明关键性质，尽可能早地发现隐蔽错误。
-   **文字规则、技能文件与 Agent 指令：**用于表达需要判断力的要求，但不应成为处理已知问题的首选手段。

验证不仅能发现程序错误，还能检查系统必须保持的属性和不变量，同时帮助判断 Agent 是否真正理解了目标和意图。验证工具可以叠加使用，形成从静态检查到运行时行为、再到形式化性质的完整防线。

## 优先把纠正沉淀为确定性检查

代码库是 Agent 最大的输入之一。Agent 根据输入生成输出，因此输入质量直接决定输出质量。每当需要纠正 Agent 时，不应只是在规则文件或 Agent 指令中再增加一行说明，而应优先思考：能否把这次纠正转化为可复现的确定性检查？

写进代码中的约束比写在提示词或 Markdown 规则里的要求更可靠，因为它们可以重复执行、统一报错，并且更容易被审计。凡是能够通过 API 设计、架构重构、Lint 规则、类型约束或测试表达的问题，都应尽量沉淀到代码库本身。

## 代码库像花园：反模式会像杂草一样扩散

过去，一个工程师可能每天审查几个 PR；如今，Agent 让单个工程师能够协调由数百甚至数千个 Agent 组成的团队，代码生成速度接近持续的溪流。随着代码越来越像有机生长的系统，软件工程也更像园艺工作。

在这个比喻中，代码库是花园，API、架构、Lint 规则和验证机制是护栏与混凝土基础。旧代码中的变通方案、反模式、弃用接口和技术债务，都可能被后续 Agent 当作既有范例直接复制。花园里长出一株杂草后，如果不及早清理，问题很快就会蔓延到更多代码。

因此，保持代码库纯净是提高 Agent 产出质量的重要前提。应持续清理过时模式，避免给 Agent 留下可以模仿的坏样本。

## 实例一：用架构与 Lint 限制高风险 API

在面向桌面应用的客户端框架中，团队将构建过程中积累的经验编码为 API 设计和 Lint 规则。一个典型例子是 React 的 `useEffect`：它有合理用途，但需要开发者准确理解依赖关系、执行时机和清理逻辑，使用不当很容易造成混乱。

由于 Agent 往往不擅长处理这类需要细微判断的 API，团队直接在产品代码中禁止使用，只允许在特定底层 API 内部按明确方式调用。这样做把原本需要反复代码审查的注意事项，变成了自动拦截规则，问题也随之减少。

![[笔记同步助手/images/edd093d60eb9e28c462d7f7d5d5bf0ba_MD5.jpg|通过 Lint 规则限制 React useEffect 等高风险 API]]

## 实例二：用目录结构表达上下文

在 Electron 应用中，Agent 经常把主线程代码导入渲染器线程，导致长任务、界面卡顿和性能下降。团队随后采用两个顶层目录，分别隔离 `electron-main` 与 `electron-renderer` 的职责，并使用依赖关系图分析器和 Lint 规则禁止两个目录相互导入。

这类规则配置简单，却把一条重要的架构边界变成了机器可执行的约束。结果是代码审查者不必反复检查同一类错误，Agent 也能从目录结构和静态检查中理解上下文。

## 实例三：不要让 Agent 用注释为临时补丁辩护

Agent 很喜欢使用 Markdown 文档、代码注释和技能规则来解释自己没有执行正确操作的原因，甚至会把一次微小修正理解成永远不能违反的硬规则。在 Cursor 项目中，Agent 曾大量使用 `setTimeout`、`requestAnimationFrame` 和 `requestIdleCallback` 等命令式计时器，作为 React 声明式架构冲突的快速修复方案。

这种补丁会掩盖真正的架构问题。大量计时器被快速创建和销毁时，会带来严重垃圾回收、延迟和卡顿。更危险的是，Agent 还会添加大量注释，说明这些临时方案为何合理，使错误方案看起来像是有意为之的长期设计。

## 为什么禁止 99% 的注释

团队在相关项目中决定禁止约 99% 的注释，原因是注释很容易过时，而且人类通常不会认真阅读堆积的说明。更重要的是，注释无法被强制执行：Agent 可以写下“不要做某事”，却仍然继续做某事；注释还会给 Agent 留出一个逃生口，用来为不执行正确操作寻找借口。

真正可靠的约束应当由 Lint 规则、类型系统、测试和验证工具来承担。与其用注释提醒下一个 Agent“修复根本原因，而不是在周围打补丁”，不如让检查器直接拒绝这种绕过根因的修改，并给出清晰、可操作的错误信息。

这一原则可以概括为：**每当纠正 Agent，都把纠正转化为确定性检查，或者通过更好的 API 设计和架构消除问题根源。**当这一过程反复进行，代码审查需要关注的事项会越来越少，最终可以让 Agent 自动合并大部分 PR。

![[笔记同步助手/images/3c06752ffbbd99af8c3d02b10d08138e_MD5.jpg|从不可执行的注释转向可强制执行的 Lint 检查]]

## 验证：让 Agent 能够自主工作

验证是提升 Agent 自主性和可信度的基础。代码审查流程不再只关注代码差异本身，而是重点检查验证产物，例如运行结果、截图、图表、测试报告和形式化验证结论。

### 运行时验证

运行时验证让 Agent 像人类开发者一样运行应用并使用调试工具，例如 Chrome DevTools Protocol。它能够验证真实交互、性能和用户可见行为，而不仅是检查静态代码。

团队在运行时验证技能中加入了“功能映射”：从用户视角列出应用中所有可用功能及其位置，为 Agent 提供共享词汇，避免它猜测“左侧边栏里的那个东西”究竟指什么。

他们还为 Agent 提供统一的 CLI 和驱动程序，使每次验证都能重复使用相同的工具。这既减少了 Token 消耗，也提高了验证过程的可测试性。

### 形式化验证

团队也开始使用 TLA+ 对主要用户流程进行模型检查，例如跨多个设备和平台的通知流程；还使用 Lean 等工具证明某些算法的性质，例如在自定义虚拟化库中检查闪烁或抖动问题。

形式化验证不是万能药，但它是 Agent 环境中的另一层防线。到目前为止，它已经帮助团队发现了不少错误。形式化模型还迫使团队明确描述产品应该如何运作，从而检验 Agent 是否真正理解了系统意图。

## 70% 的 Token 用于验证

视频引用了一条关于 Agent 验证投入的讨论：几个月前，团队因为隐蔽错误被合并而无法信任 Agent；半年后，团队每天约 70% 的 Token 都用于验证。演讲者的观察与之相符：其团队的大部分 Token 消耗也集中在验证环节。

这些方法本身并不是新技术，它们是成熟的软件工程工具。过去，编写、理解和维护验证工具的成本高到令人却步；Agent 则显著降低了自动化测试和验证的成本，使过去经济上不可行的全面检查变得可行。

因此，软件测试与验证正在进入更适合 Agent 的阶段。验证不仅用于发现问题，也能帮助产品团队思考系统应满足的性质，并检查 Agent 是否准确理解目标。

## 从代码审查到状态机可视化

为了让复杂行为更容易审查，团队开发了状态机技能，结合视频和截图，从用户视角可视化系统状态。用户不必只阅读 Agent 生成的代码，也可以直接观察状态转移和交互结果，从而更容易发现异常路径。

这类可视化审查把抽象代码转换成用户能够理解的行为证据，是验证流程的重要补充。

## 结果：高速交付没有牺牲质量

在相关团队中，交付速度显著提升：上个月向生产环境发布了约 11,000 个 PR，客户端发布节奏加快到大约每天一个稳定版本，核心团队的交付量也明显增加。10 月份约有 227 名贡献者至少提交过一个 PR，其中既有核心成员，也有背景信息有限、偶尔参与项目的贡献者。

尽管 PR 数量巨大，被撤回的 PR 比例反而稳定在约 0.5%。产品性能也没有因为交付提速而恶化；启动、输入、打开新会话和切换会话等操作反而更快。即使产品仍受 Electron 性能上限约束，其交互速度也已优于许多其他 Agent 用户界面。

这说明真正值得追求的不是“软件工厂”这个名称，而是一个以高质量代码库为前提、能够自我验证并持续反馈的外部循环。

## 构建 Agent 外部循环

当代码库具备足够高的质量、可靠的验证机制和清晰的架构边界后，自动化闭环才真正安全：Agent 可以启动新项目，对完整应用和构建流程进行模糊测试，像真实用户一样运行应用并发现错误，再为每个问题提交修复 PR，并在验证通过后自动合并。

这一闭环依赖大量连接器和流程编排能力，可同时运行数百甚至数千个 Agent。之所以敢于提高自动化程度，是因为默认生成的代码已经足够可靠，而且大多数产品变更并不需要同等强度的人工审查。

核心不是让 Agent 获得更多权限，而是先让它在受约束、可验证的环境中证明自己。

## 实践清单

-   把代码库视为 Agent 的主要输入，优先清理反模式、过时 API 和技术债务。
-   每当发现 Agent 的错误，先问能否用 Lint、类型系统、编译器、测试或架构边界进行硬性约束。
-   用清晰的 API 设计和目录结构表达上下文，降低 Agent 猜测代码用途的概率。
-   不要依赖注释、文档或 Agent 指令来执行关键约束；它们可以解释意图，但不能可靠阻止错误。
-   建立运行时验证，让 Agent 自动运行应用并使用与开发者相同的调试工具。
-   维护功能映射和统一 CLI，帮助 Agent 稳定理解用户功能并降低 Token 消耗。
-   对关键流程逐步加入形式化验证和基于属性的 UI 测试。
-   把验证产物作为主要审查对象，而不是反复人工检查同类低级错误。
-   只有在代码库质量、静态分析、运行时验证和形式化验证成熟后，才扩大自动化和自动合并范围。

## 结论

如果内部编码循环持续产出劣质代码，自动化只会更快地制造更多劣质代码，并消耗更多 Token。要实现高质量、高速度的交付，必须先建设可靠的代码库和验证体系，把常见错误转化为机器可执行的约束，再让 Agent 承担更大范围的实现、测试、修复与合并工作。

“别人的代码都是垃圾”并非否定协作，而是提醒开发者：如果不主动建设 Agent 环境，Agent 只会放大代码库中已有的问题。成熟的环境能让原本像垃圾一样涌入的代码，逐步转化为可以信任、可以持续演进的资产。

## 全文整理

我叫 Potato，目前在 Figma 从事 Graphite 的工作。

请大家快速举一下手：有多少人曾经看过别人写的代码，然后心想“这写的都是垃圾”？我也有过这种感受。但今天我想说服你们，你们可以把那些“垃圾”变成黄金。

上个月，我做了一件疯狂的事：向生产环境提交了三千个拉取请求。

在 Agent 出现之前，我们从未真正关心过代码量，除非遇到某些特例。在我之前任职的公司，人们把这些人称为“编码机器”。比如 Bret Taylor，他曾因在周末重写整个 Google Maps 而闻名，是一位效率惊人的工程师。

现在，有了 Agent，任何人都可以成为一台编码机器。

我的观点是，软件工程师的工作，或者说软件工程师的主要职责，在于弄清楚如何在大幅提升生产力的同时，保持甚至提高代码质量。

有些人喜欢把这种方式称为“软件工厂”，但我更喜欢简单一点。我认为，这件事完全关乎信任。

不是盲目地信任，而是投入精力构建你的 Agent 环境，这样你才能确信自己的 Agent 会做出正确的操作。要达到这一步，需要付出相当大的努力。我花了六个月，才达到可以发布数千个拉取请求的程度，其中很多是在我睡觉时完成的。但这绝对是可能的，而且你所花的时间会比我少得多。

### 从低信任环境走向高信任环境

先来谈谈我们如何从低信任环境走向高信任环境。

这个倒金字塔，是我思考如何投入时间构建 Agent 环境的方式。

最下面两层是确定性的，也就是直接利用代码本身。比如良好的 API 设计、架构重构，或者使用 Lint 规则、类型系统、编译器，以及各种不同类型的测试。

你可以结合使用这两层机制，限制 Agent 的行为，强制它们默认采取正确操作。

验证，包括运行时验证和形式化验证，是很好的工具。它们可以叠加使用，用来发现错误，检查系统中希望保持成立的属性和不变量，同时也能帮助你检查 Agent 是否真正理解了你的目标和意图。

最后，你还需要加入一些文字说明，例如规则、技能和 AGENTS.md，以及那些需要判断力才能处理的事情。

但让我们先从代码库开始。

Agent 根据输入生成输出，因此输入的质量至关重要，而代码库正是其中最大的输入之一。

因此，每当你纠正 Agent 时，都应考虑如何把这次纠正变成一个确定性检查，而不是在规则或 AGENTS.md 中再增加一行。因为约束一旦写进代码，就更具可复现性，也更值得信任。

我喜欢的类比是：代码库就像一座花园。

过去，代码通常一次只到来几个拉取请求。我记得 2024 年开始工作时，回去审查同事写的三个拉取请求，就已经需要投入不少精力。而今天，这个数字更接近三百。

所以，现在每位工程师都相当于一个由数百甚至数千名成员组成的团队。代码到来的速度如此之快，感觉就像一股持续不断的水流，几乎是有机的，像一个活生生的东西。

在这个类比中，代码库就是 Agent 编写的代码赖以生长的混凝土基础，就像图片里的建筑一样。你施加在代码库上的约束、设置的护栏，就是这个基础。

因此，在许多方面，软件工程师的工作正变得有点像园艺，因为代码是 Agent 最大的输入。

这意味着，任何变通方法、反模式、废弃代码和技术债务，都很可能被下一个 Agent 直接复制，因为它看起来像是代码库中既有的模式。

这就像花园里长出了杂草或害虫，在你意识到之前，它们就已经蔓延到各处。

因此，你希望代码库尽可能保持纯净，让 Agent 始终能够复制到好的内容。

### 用代码约束 Agent

下面来看一些真实的例子。

Graphite 是我们为 Graphite HD 创建的一个客户端框架，旨在实现这种“有机架构”的理念。从技术上看，它并没有那么有趣，可以把它看作类似 Electron 应用的 Next.js。

真正有趣的地方在于，它包含许多约束和 Lint 规则，我们将构建桌面应用时学到的许多经验教训都编码在其中。

其中一个教训是：任何需要细微把握才能用好的东西，往往都会导致混乱。

一个经典例子是 React 中的 `useEffect`。它有自身的适用场景，但经常被误用。有人开玩笑说，使用 `useEffect` 需要博士学位；换个说法，它确实需要很多细微的把握才能用好，而 Agent 并不擅长使用它。

所以，我们的解决方案是直接在产品代码中禁止使用它，只允许在对内部 API 的某些地方使用。现在，这个问题已经被彻底消除了，我们再也不需要在代码审查中处理它。

我们使用的另一个有趣模式，是通过目录结构来表达上下文。

我们在 Cursor——一个 Electron 应用——中看到的一个反模式是，Agent 经常把主线程代码导入渲染器进程，从而导致长任务和卡顿。

因此，在 Graphite 和相关子应用中，我们已经把正确做法确立为一项非常明确的规范。我们设置了两个顶层目录，分别叫 `electron-renderer` 和 `electron-main`。我们的依赖关系图分析器和一些 Lint 规则禁止它们相互导入。

这些 Lint 规则设置起来很简单，但这样一来，代码审查时需要审查和考虑的事情就少了一件。

还有一件让我感到意外的事：Agent 会利用 Markdown，例如文档、代码注释和技能规则，记录自己没有执行正确操作的理由。

你是否也见过这种情况？Agent 会对一些小修正过度反应，并把它视为一条永远不能打破的硬性规则。

这是另一个来自 Cursor 的例子。

Agent 非常喜欢使用命令式计时器，例如 `setTimeout`、`requestAnimationFrame` 和 `requestIdleCallback`。它们会使用这些计时器作为快速修复方案，因为实际上，它们是在修补 VS Code 的命令式风格与 React 的声明式风格之间的架构冲突。

结果往往是，我们对架构的选择反而让客户端和 Agent 的性能都变得更差。

如果你做过 JavaScript 性能优化，就会知道，当大量计时器被快速创建和销毁时，会引发大量垃圾回收，造成严重的延迟和卡顿。

更糟糕的是，Agent 写了很多代码注释，就像图中红色部分展示的那样，解释为什么这种快速修复是合理的。不知不觉间，计时器开始到处泛滥，应用的性能确实受到了严重影响。

现在，我们在 Graphite 中吸取了教训，决定禁止 99% 的注释，因为它们很容易过时，而且人类根本懒得阅读那些堆砌出来的注释。

注释还会给 Agent 留出一个逃生口，让它可以为了不做正确的事而寻找借口，毕竟那很难。

关于注释，最糟糕的一点是，它们无法被强制执行。所以，那些看似出于好意的说明——比如“我想告诉下一个 Agent 不要做某事”——最终往往无法成为你可以信赖的约束。

因此，在 Graphite 和相关项目中，我们现在会使用 Lint 规则，提供清晰且非常有帮助的错误消息，告诉 Agent 去修复根本原因，也就是真正的问题，而不是只在问题周围打补丁。

我们的基本原则是：每当我们纠正 Agent 时，它要么会变成一个确定性检查，要么我们会考虑如何通过更好的 API 设计和更好的架构，从根本上消除代码中的那个问题。

如果你这样做足够多次，就会发现代码审查中需要注意的事情越来越少。到了某个时刻，你会发现已经没有什么需要审查的了，这时就可以直接让 Agent 合并它们的大部分拉取请求。

### 用验证建立信任

验证也是让 Agent 更有自主性，并增强我们对其工作信心和信任的重要组成部分。

我们的代码审查流程现在已经被简化为查看验证产物，例如视频、截图、图表和形式化验证结果。

最基本的例子是运行时验证。用更准确的话说，就是让你的 Agent 自行运行代码，并使用人类开发者也会使用的调试工具，比如 Chrome DevTools Protocol。

在我们的运行时验证技能中，有一种叫作“功能映射”的机制。它本质上是一份网站地图，从用户视角列出应用中的所有可用功能。

有了它，Agent 就不必猜测你提到左侧边栏里的某个东西时究竟指的是什么。功能映射为 Agent 提供了共享词汇。

我们还在这些技能中使用自定义 CLI，使 Agent 每次都可以重复使用同一套 CLI 和驱动程序。这不仅减少了 Token 消耗，也让整套流程具备可测试性。

最近，我们也开始研究形式化验证。目前，我们使用 TLA+ 对主要用户流程进行模型检查，例如跨多个设备和平台的通知。

我们还使用 Lean 来证明某些算法的性质。比如，我们编写了自己的自定义虚拟化库，并使用 Lean 对其进行检查，以确保不会出现闪烁或抖动问题。

我们仍在总体上探索这种方法。它看起来非常有前景，而且我们已经通过形式化验证发现了不少错误。

当然，它不是万能药。我们把它视为另一种工具，是 Agent 环境中的另一层保障。

这是一个节奏很快的视频。我们刚开始研究的另一件事，是针对 UI 的基于属性的测试。我们使用了一个名为 Somewhat 的库，它也已经帮助我们发现了一些 UI 错误。

从宏观角度看，我看到 Cindy 的一条推文。六个月前，他提到自己无法信任 Agent，因为一些隐蔽的错误被合并进了代码。要真正信任自己的 Agent，他所缺少的其实是验证流程。

六个月过去了，他说自己每天 70% 的 Token 都用于验证。我认为，这与我的观察一致：我大部分的 Token 使用量也都花在验证上。

如果仔细审视这里提到的任何内容，它们都不是我们以前从未见过的新颖技术，只是一些优秀的软件工程工具。但在过去，使用这些工具的成本高得令人望而却步，因为它们难以理解、编写或维护。

Agent 大幅降低了这部分成本。我们确实正在进入软件测试和验证的黄金时代，因为 Agent 让我们能够以远超以往经济可行性的程度对一切进行测试。

此外，形式化验证还可以帮助你更好地推理产品应当如何运作，以及 Agent 是否真正理解了你的意图和目标。

### 从用户视角审查状态

我们还创建了一个名为“状态图”的新技能。在我的项目 `potato-sec` 中，它可以帮助你从用户视角可视化状态机。

我发现，把这项技能与我们提供的视频和截图结合起来，审查起来会容易得多，所以它非常有用。

### 高信任环境带来的结果

现在来看看理想境界是什么样，以及对这些投入最终能够得到什么回报。

在 Graphite 团队，我们的开发速度正在起飞并迅速提升。上个月，团队向生产环境发布了惊人的 11,000 个拉取请求。这是一个疯狂的速度，而且我们发布客户端的节奏也加快了。我们大约每天都会发布一个新的稳定版本。

此外，核心团队的交付量也大幅增加。我们还有很多非正式或偶尔参与的贡献者，他们并不总是掌握很多背景信息，但同样在做出贡献。

十月份，我们大约有 227 人贡献了至少一个拉取请求。

开发速度加快，会不会意味着交付速度也会加快？实际上，被撤回的 PR 数量反而降低了，并稳定在 0.5% 左右。

但真正有趣的不是交付节奏和拉取请求数量，而是 Graphite 的性能不仅保持稳定，而且与我们刚刚发布时相比，在多个维度上都有所提升。

启动应用、打开新对话、切换对话，所有这些操作都变得更快。

请记住，Graphite 目前仍然是一款 Electron 应用，因此仍然存在性能上限。但它已经比市面上许多其他 Agent 用户界面快得多。对于一款拥有如此高开发速度、并且有这么多人参与贡献的 Electron 应用来说，我认为这已经相当不错了。

### 在构建软件工厂之前，先改进代码库

因此，在急于构建软件工厂、尽可能自动化一切之前，每当你需要修正 Agent 时，请先尝试通过改进代码库来解决。

你可以先添加一条 Lint 规则，防止反模式再次出现，然后逐步清理那些旧模式。接着，确保自己的验证机制足够稳健。

这些工作大多是实现自动化的前提。如果内部编码循环产出的是劣质代码，自动化只会产生更多劣质代码，并消耗更多 Token。这非常昂贵。

一旦你对代码库进行静态分析、运行时验证和形式化验证这些投入，就会发现有了这些基础，许多事情都变得可能，而且你确实可以很轻松地在这些基础上构建自己的工厂。

当你准备好时，Graphite 是构建这类外部循环的绝佳方式。我们有大量连接器和流程，可以启动 Cursor 云端项目，让你能够编排数百甚至数千个 Agent。

举一个简单的例子：现在每当我们发布一个新版本时，Graphite 都会自动为我们启动一个新的 Cursor 项目。它会对整个应用程序和整个构建过程进行模糊测试，并通过运行应用、像真实用户一样使用它来发现错误。

随后，针对发现的每一个错误，它都会提交修复后的 PR，并自动合并这些 PR。

尽管这听起来很疯狂，但这是因为我们的代码库质量足够高，拉取请求通常默认就是高质量的；而我们合并的大多数产品代码，实际上并不真正需要深入的人工审查。

当你拥有坚实的基础和良好的有机架构时，就能在不牺牲质量的前提下实现快速交付，让腐朽神奇般转化为黄金。

当所有事情都变得如此轻松时，你甚至可以把整个流程称为软件工厂。
