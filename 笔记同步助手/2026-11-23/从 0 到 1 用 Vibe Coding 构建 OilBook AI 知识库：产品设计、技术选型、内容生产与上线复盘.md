**作者：**oil欧呦

**视频主题：**本笔记整理了作者从需求分析、产品定位、视觉设计、技术选型，到业务功能开发、登录与支付、课程内容生产、部署上线及邮件通知的全过程，重点分享如何借助 Vibe Coding 与 AI Agent 独立开发一个可公开访问的 AI 知识库网站 OilBook。

## 一、为什么要做一个 AI 知识库

作者制作 OilBook 的直接原因是需要长期沉淀自己的文字内容。短视频虽然传播方便，但历史视频在平台上的检索能力有限，文字密度也相对较低；同时，作者希望将一部分内容整理为付费内容，因此需要一个独立的内容载体。

虽然市面上已有许多知识库、专栏和内容平台，作者仍然决定从零开发独立网站，主要基于以下三点考虑。

### 1\. 独立网站更容易被发现和转化

新网站通常没有自然流量，但公开网站比封闭平台更容易在演示产品时被访问，也可以通过搜索引擎获得曝光。相比将用户从社交平台引导到另一个私域平台，独立站点之间的转化路径更直接。

![[笔记同步助手/images/16db533e1e7f6b292d32f193def1469d_MD5.jpg|演示 OilBook 独立网站与知识库产品形态]]

演示 OilBook 独立网站与知识库产品形态

### 2\. 内容呈现和交互方式可以完全定制

作者希望自由调整衬线字体与非衬线字体、字号、行距、字间距、明暗主题、目录结构和朗读功能，不受第三方平台模板限制。对于以长文阅读为核心的知识库，可读性和阅读舒适度需要优先考虑。

### 3\. 熟悉的技术与支付经验可以直接复用

作者已经具备独立开发和支付接入经验，在这个前提下开发自己的产品，通常比学习并适配另一套陌生产品更容易。

## 二、整体技术架构

项目采用一套前后端一体的技术栈，核心方案如下：

-   **应用框架：**Next.js，负责前端页面、服务端接口以及部分后端逻辑。
-   **数据库：**Neon，提供云端 PostgreSQL 服务。
-   **内容存储：**课程文章以本地 Markdown 文件保存，通过 Next.js 直接渲染，不额外引入 CMS。
-   **代码托管：**GitHub。
-   **部署平台：**Vercel，推送代码后自动部署。
-   **域名与 DNS：**Cloudflare。
-   **邮件服务：**Resend。
-   **登录与支付：**Google OAuth、邮箱免密登录及 Stripe。

![[笔记同步助手/images/5e4847eeaa7698ee39626520d2186f30_MD5.jpg|OilBook 技术架构与核心工具]]

OilBook 技术架构与核心工具

### 为什么选择 Next.js

Next.js 是主流前端框架，也能承担服务端接口工作，适合前后端一体化开发；内容增多后，对搜索引擎爬取和 SEO 更友好。代码、页面与接口位于同一仓库，也降低了 AI 协作开发时的上下文复杂度。

### 为什么选择 Neon

Neon 与 Supabase 都提供云端 PostgreSQL 数据库。Neon 的免费数据库不限制项目数量，适合同时维护多个用量不高的产品；Supabase 免费方案的项目数量限制更明显。Neon 的核心价值首先是节省成本和降低运维复杂度。

![[笔记同步助手/images/fe793edbda37277ddd0bad8f30978023_MD5.jpg|Neon 云端 PostgreSQL 数据库配置]]

Neon 云端 PostgreSQL 数据库配置

### 为什么不用 CMS

当前文章数量有限，作者可以让 AI 将草稿整理成 Markdown，再直接修改本地文件。相比引入完整的内容管理框架，本地 Markdown 更容易维护，也方便 AI 读取工作区中的既有文章作为写作上下文。

![[笔记同步助手/images/606a8f64eadbff64b152381f0c86cd76_MD5.jpg|本地 Markdown 文件与 AI 整理课程文章]]

## 三、如何向 AI 描述需求

需求描述可以保持口语化，但至少应明确四件事：

1.  要开发的产品及其核心目标。
2.  使用的前后端框架。
3.  数据库方案。
4.  内容的存储和维护方式。

例如，可以直接告诉 AI：使用 Next.js 和 Neon，从零开发一个个人知识库网站；文章不存入数据库，而是放在本地 Markdown 文件中维护。在技术方案明确后，再进入产品设计和功能实现阶段。

## 四、产品定位与视觉设计

### 1\. 先确定产品隐喻

知识库可以表现为博客、知识星球式社区，也可以表现为书籍。作者选择“书籍”作为主要意象：与“知识库”这一抽象概念相比，书本更直观，也更容易形成鲜明的视觉记忆。

作者先使用自己的 Skill 和 UI 工具派生出三个视觉方向，再从中选择：

-   现代清爽的博客风。
-   轻巧的杂志、小册子风。
-   古典沉稳、带有纸张质感与书架意象的书本风。

最终采用偏拟物的书本设计，以增强辨识度。

## 五、提升长文阅读体验

知识库的核心产品形态是文字阅读，因此文章详情页的可读性比单纯追求视觉效果更重要。作者围绕以下细节反复调整：

-   使用略微偏暖的页面颜色，降低长时间阅读的视觉疲劳。
-   提供白天与黑夜模式切换。
-   优化 Markdown 标题、代码块和引用块的渲染，减少过多边框与嵌套。
-   统一正文、顶部按钮、订阅按钮等组件的视觉语言。
-   适当增大字间距和行高，让页面更疏松，避免文字密集。
-   控制段落长度：既不一句一行，也不形成难以阅读的长段。
-   增加文章目录，降低长文定位成本。

![[笔记同步助手/images/b0a376cf732c3ca157507d2617a4537c_MD5.jpg|文章详情页目录、暖色阅读主题与正文排版]]

## 六、用 AI Agent 开发业务功能

在前后端业务开发阶段，作者主要使用自己开源的 OilDev Skill。该 Skill 包含多个子 Skill，分别服务于规划、代码审查和项目治理等环节。

### 1\. Oil Plan：先形成可理解的业务方案

新增功能前，先让 AI 编写实施方案，再由独立子 Agent 审查。相比只输出技术术语，Oil Plan 更强调业务目标、用户流程、影响范围和可执行步骤，使开发者能够判断接下来数小时的开发工作。

例如在登录、收款和付费墙需求中，方案应明确：

-   用户如何注册、登录和恢复访问。
-   哪些内容属于 Pro 会员专属。
-   支付成功、失败或取消后如何更新权限。
-   付费内容如何从服务端进行保护。

### 2\. 子 Agent Review：补全遗漏

第一次生成的方案可能遗漏业务细节。让独立子 Agent 以 Review 角色重新检查，可以补充边界条件，并发现原方案中的不完整之处。

### 3\. Oil Code Review：实现后审查代码

功能实现后，AI 会依据项目规范执行代码检查，发现问题后直接修复。对于复杂度较高的项目，还可以使用 Oil Exploit，派发多个子 Agent 并行探索代码和潜在风险。

### 4\. Oil Government：维护项目文档与规范

项目中需要维护 `AGENTS.md`、课程写作规范、插图规范、发布规范等文件。开发过程中，如果 AI 误解了要求或重复犯错，应在修复问题的同时更新对应规范，使后续协作不再依赖用户反复输入相同要求。

## 七、登录、支付与付费墙

### 1\. 邮箱免密登录

后端没有引入完整第三方登录框架，而是利用 Next.js 服务端接口和 Neon 数据库实现轻量方案。邮箱免密登录需要接入外部邮件服务，作者使用 Resend 发送登录邮件。

![[笔记同步助手/images/69f3b19297760e43990424cf950b0298_MD5.jpg|Next.js、Neon 与 Resend 邮箱免密登录流程]]

Next.js、Neon 与 Resend 邮箱免密登录流程

### 2\. Google 登录

Google 登录需要在 Google Cloud 的凭据控制台创建 OAuth 客户端，并填写网站地址及登录后的回调地址。后端接入 Google 官方认证接口后，AI 可以协助完成配置。对于部分控制台操作，也可以使用浏览器自动化完成。

### 3\. Stripe 收款

网站提供 Pro 会员和部分付费内容，作者使用 Stripe 收款。Stripe 的优势是接入流程成熟，并可配合插件、CLI 或 MCP 工具完成产品创建与联调。

自动化适合处理技术接入，但产品决策仍应由人完成，包括：

-   采用买断制还是订阅制。
-   会员价格与课程价格。
-   是否提供优惠码或试用。
-   不同内容与会员等级之间的权限关系。

![[笔记同步助手/images/cb065e758030d88a49d098f5ef207e81_MD5.jpg|Stripe 产品、订阅与支付配置]]

Stripe 产品、订阅与支付配置

### 4\. 付费内容必须由服务端保护

付费段落不能只通过前端 CSS 隐藏，也不能在未鉴权时由后端接口完整返回。正确做法是同时校验登录状态与会员权限，仅向有权限的用户返回完整内容。

这一环节应让 AI 从前端、后端、接口响应和日志等角度审查，避免出现业务数据泄露。还应直接调用接口验证未付费用户无法取得受保护正文。

## 八、从历史视频到系统化课程

网站框架完成后，内容生产成为新的核心任务。作者过去发布的视频通常包含字幕、文字稿和脚本，因此可以让 AI 扫描历史内容，再归纳系统化的课程选题。

### 为什么不直接让 AI 整理旧视频

直接把手播稿改成课程文章虽然简单，但存在四个问题：

1.  **信息密度不足：**二三十分钟的口播内容，写成课程后可能只有几百字。
2.  **讲述逻辑不一致：**AI 重写后的结构不一定符合作者原本的思考顺序和表达习惯。
3.  **文字应当是视频的超级浓缩：**文字可以减少铺垫，用更高的信息密度承载核心结论。
4.  **旧内容存在时效性问题：**模型推荐、旧工具和过往判断可能已经过时，不能把历史表述直接当作当前观点。

![[笔记同步助手/images/1fb7237228d02ce1ba05f4e9105a8ea6_MD5.jpg|历史视频字幕与脚本转化为系统化课程选题]]

## 九、访谈式写作与最小化改写

### 1\. 让 AI 担任采访者

撰写新课程时，作者采用访谈式写作：AI 根据主题提出问题，作者通过语音输入回答当下真实使用的工具、实践过程和判断。完成全部访谈后，AI 再把口述内容整理为正式章节。

关键约束是：每轮口述原文必须完整保留，不能在讨论过程中擅自改写；正式整理时只允许最小化调整，不应额外加入事实、观点或戏剧化表达。

![[笔记同步助手/images/7a7d8b5e3b2e064769b7892f454429fc_MD5.jpg|AI 提问、作者语音回答的访谈式课程写作流程]]

AI 提问、作者语音回答的访谈式课程写作流程

### 2\. 用脚本检查“AI 味”

即使给出明确提示，长对话中模型仍可能逐渐偏离要求。作者编写了文案审查脚本，维护一组不允许出现的词语或表达，并在文章完成后自动检查。常见问题包括：

-   “发现一个很具体的问题”等过度具体、模板化的开头。
-   “原因很现实”“非常直接”等生硬过渡。
-   “我现在用大白话告诉你”“给你掰开揉碎讲清楚”等自我解释。
-   刻意拟人化、夸张或用力过猛的动词和修饰。
-   过多使用“底层”“脾气”“焊死”等不自然的表达。

脚本只能处理可模式化的用词问题，不能替代人工通读。

![[笔记同步助手/images/c622fbacc95674cf22fd7c501d7db706_MD5.jpg|文案审查脚本与 AI 味表达检查结果]]

文案审查脚本与 AI 味表达检查结果

### 3\. 子 Agent 进行两类 Review

每篇文章完成后，再交给独立子 Agent 检查：

-   **衔接检查：**通读全文，检查段落过渡是否自然，是否存在机械拼接。
-   **读者视角检查：**假设读者不了解相关背景，检查是否突然引入复杂概念、函数参数或缺少必要铺垫。

若发现理解障碍，可选择增加解释、补充前置知识，或加入图示降低理解难度。

## 十、图文配合与 AI 生图

文章配图采用“图片与文字分离”的方式：AI 负责生成插图，图片描述则由 AI 单独撰写，而不是直接把大段文字生成在图片里。这样更便于后续修改文案和编辑图片。

AI 生图还可以用于：

-   文章插图和概念图示。
-   网站图标与 Logo。
-   书籍封面和专题封面。
-   统一风格的界面素材。

作者为封面和插图制定了专门规范，并保留每次生成使用的提示词。后续生成时，要求新图片不与现有素材重复，而是基于同一风格继续探索。

## 十一、部署、域名与自动上线

代码托管在 GitHub，GitHub 与 Vercel 连接。每次推送新代码，Vercel 会自动触发构建和部署。域名在 Cloudflare 购买或管理，并为 Vercel 配置对应的子域名解析。

这种结构形成了完整链路：

1.  本地维护 Next.js 与 Markdown 内容。
2.  将代码推送到 GitHub。
3.  Vercel 自动构建并上线。
4.  Cloudflare 将子域名解析到 Vercel。
5.  用户通过固定域名访问网站。

## 十二、Newsletter 与邮件模板

网站上线新文章或新课程后，可以向符合条件的用户发送 Newsletter。系统通过数据库筛选已登录并同意接收通知的用户，再由脚本调用 Resend 发送邮件。

邮件体验也会影响产品成熟感，因此可以预先设计 HTML 模板，包括：

-   新课程上线通知。
-   新文章发布通知。
-   登录验证码邮件。
-   会员购买成功或续费通知。

上线前应让 AI 向自己的账号发送测试邮件，检查桌面端与移动端的排版、链接、深色模式适配和文本可读性。

## 十三、可复用的 Vibe Coding 工作流

1.  **先定义问题：**明确用户是谁、为什么需要产品，以及要沉淀或商业化什么内容。
2.  **确定产品隐喻：**从博客、社区、杂志或书籍等方向中选择最符合品牌气质的表达。
3.  **建立设计系统：**让 AI 生成多套方向，确定视觉方案后将规则沉淀为 `DESIGN.md`。
4.  **锁定技术方案：**明确框架、数据库、内容存储和部署方式，避免无必要地增加复杂度。
5.  **先规划再实现：**让 AI 编写业务可读的方案，并通过子 Agent Review 补全细节。
6.  **实现后持续审查：**执行代码 Review，重点检查权限、安全和业务边界。
7.  **把经验写回规范：**每次纠正 AI 的问题后，都同步更新项目文档。
8.  **保护付费内容：**必须在服务端完成鉴权与内容裁剪，不能只做前端遮挡。
9.  **用访谈生产内容：**让 AI 提问，作者口述真实观点，再进行最小化整理。
10.  **检查 AI 味：**结合脚本检查与独立 Agent Review，再由人工最终通读。
11.  **自动化部署和通知：**通过 GitHub、Vercel、Cloudflare、Resend 和数据库形成稳定发布链路。

这套流程的关键并不只是“让 AI 写代码”，而是建立清晰的产品判断、设计规范、业务计划、项目文档和安全边界，让 AI 在稳定上下文中持续参与开发。

## 全文整理

大家好，今天这期视频给大家分享一下，我是如何从零到一用 Vibe Coding 开发出 OilBook 这个 AI 知识库网站的。我会完整介绍自己如何进行产品设计、产品开发、课程编写、上线发布，以及接入支付。希望我的开发过程能对大家自己用 Vibe Coding 开发项目有所帮助。这些内容的文字版本已经放进 OilBook，主题就是《从零到一开发 OilBook 的实战复盘》。

在开发一个产品之前，首先要进行需求分析：为什么要做这个产品？它是什么形态的产品？最终要包装成什么概念？我之所以要做 AI 知识库，是因为需要沉淀自己积累的文字内容。虽然我发布了很多视频，但在各类平台上很难搜索到以前发布的存量视频，而且视频的文字密度没有那么高。另外，我有一部分内容可以做成付费内容，所以需要一个以文字为主的知识库。

为什么不直接使用现成的平台？目前市面上已经有很多知识库工具和专栏平台，但我最后还是决定从零开发一个独立网站，主要有三个考虑。

第一，这类平台刚开始运营时不会自带流量，也没有自然流量。如果使用现成的知识库工具，就很难在自媒体平台或社交媒体平台上完成转化。因为在自媒体平台、社交媒体平台把用户从公域引流到私域，转换难度很高。而做成一个公开网站后，在演示产品时，用户天然更容易发现你的产品，也知道如何访问。网站还可以直接通过搜索引擎查到。相比在微信这类封闭平台中运营，这种公开网站的曝光方式更简单。

第二，内容的呈现方式和交互功能可以完全按照自己的想法定制。我开发的网站里有很多特殊功能，比如可以调整文字类型，在衬线字体和非衬线字体之间切换，也可以调整文字大小，还能提供音频朗读功能。这样的定制化程度更高，也不会受到平台模板的限制。

第三，结合我自己的开发经验以及过去接入支付的经验，开发一个产品反而比学习并使用另一个现成产品更简单。

确认大方向后，我开始设计技术栈。我选择的是自己最熟悉的一套技术栈：使用 Next.js 实现前后端一体化，使用 Neon 作为数据库。课程和文章内容全部保存在本地，通过 Markdown 直接渲染，没有使用 CMS 或其他内容托管框架。

Next.js 是目前市面上的主流前端框架之一，同时也能承担一部分后端工作。如果代码写得足够清晰，它对 SEO 曝光也比较友好。当网站上的内容逐渐增多时，搜索引擎更容易爬取到网站。对于 AI 来说，使用 Next.js 开发也很简单，因为前后端代码都放在同一个仓库中，使用的是同一个框架，而 AI 对 Next.js 也非常了解。

之所以需要数据库，是因为网站还有登录功能，也有一些数据需要存储，比如支付信息、访客量和用户反馈。

为什么选择 Neon？除了 Neon，还有一个叫 Supabase，它们都是目前比较主流的云端 PostgreSQL 数据库服务。使用它们的好处是免费数据库不限制项目数量，而 Supabase 最多只能创建两个项目。如果我的项目比较多，只要用量不高，就不需要额外付费。有些产品上线后用户不多，也不会产生费用，本质上是为了节省成本。

课程文章为什么没有做后台文章编辑器？因为现在这类文章内容很少需要手动录入，我的很多内容都是直接让 AI 整理的。只需要输入一份草稿，由 AI 整理好即可。AI 直接编辑本地 Markdown，比额外引入新的框架更简单。在编写新内容时，AI 也可以很容易地把当前本地工作区里的相关文件作为上下文召回并供参考。

我向 AI 描述需求的方式非常简单：想从零开发一个自己的知识库网站，框架使用 Next.js 和 Neon 数据库，文章不存入数据库，而是直接放在本地 Markdown 文件中维护。整个过程只需要一段非常简单的提示词。

技术方案确定下来后，接下来就是设计产品，尤其是前端。最开始，OilBook 这个名字是在探索中慢慢确定的，并不是一开始就决定要做一个书籍形态的网站。我的目标只是开发一个知识库网站。

动手之前，我会先分析知识库网站可以采用哪些视觉意象。比如，可以做成博客站，也可以做成类似知识星球的形态，或者采用我现在这种书籍意象。书籍这个意象比较抽象，但视觉呈现是直观的。因此，我会先让 AI 使用自己的 Skill UI，派生三种不同的设计风格，再从中选择自己觉得最好看的方案。这个过程非常主观。

最开始我探索了三个方向。第一种是现代、清爽的博客风，很多网站都采用这种风格。第二种是轻巧的杂志或小册子风，每个专题都像一本小册子或一本杂志。第三种是偏古典、沉稳的书本风，页面带有纸张的质感，每一篇长文都像书架上竖立的一本书。

现在网站采用的就是比较拟物的书籍设计。我认为这种风格更容易给人留下深刻印象，所以选择了这个意象。

开发这个网站时，除了放置知识内容，我还想把平时使用的模型放进“模型推荐”模块，展示给大家看。因为经常有人问我现在使用的是哪些模型，我就可以把这个模块顺便放到网站里，展示自己平时使用的模型，以及每个模型的优点和缺点。

当然，这些模块并不是一开始就设计成现在这个样子的，而是不断打磨出来的。比如，我曾让 AI 设计三种不同的模块布局：第一版把模型放在左侧展示，第二版采用另一种布局，第三版则像现在这样，在右侧以列表形式展示。现在的风格与最初设计的三版都不一样，这些设计都是逐步打磨出来的。

确定书本这一视觉方向后，我把网站命名为 OilBook。域名也选择了以“book”开头，后面加上自己个人网站的主域名，将“book”作为子域名的前缀。

接下来开始打磨网站。列表页非常简单，就是一本一本排列的书。完成列表页之后，就是详情页。

最开始让 AI 开发详情页时，它会把文字全部铺在页面中间，而且左侧没有目录，可读性并不好。对于一个以文字为主的网站，我认为可读性一定要做好。

现在网站采用略微偏暖的色调，肉眼看起来比较舒服，也可以切换黑夜模式和白天模式。

AI 最初生成的页面里还会写很多 Markdown 语法，并为不同内容渲染出很多边框。我会告诉它：“这一部分看起来太重了，不太好看了。这边的边框能不能优化一下？嵌套的边框太多了。”包括订阅按钮和顶部其他按钮，也会要求保持统一的风格。这些都是我在实际开发中使用的真实提示词。

除了减少边框嵌套，我还要求它调整文字细节。从页面上可以看到，这里的字间距比很多其他网站稍大一些，行高，也就是两行文字之间的距离，也略大一些。这样排版会更疏松，视觉上和阅读体验都会更舒服，不会产生密密麻麻的感觉。

此外，我会有意识地控制每一个段落的长度。段落不能太破碎，不能每说一句话就换一行，但也不能写得过长，否则会影响阅读体验。

像这些规范，在一点点调整完成之后，可以让 AI 配合 Oil UI 这个 Skill，将它们沉淀成一份 DESIGN.md。后续新增其他功能或调整其他页面时，就可以基于这份 DESIGN.md，确保整体风格保持一致。

整体视觉风格搭建好后，就该实现整体业务功能了。开发这类前后端业务功能时，我一般会使用自己开源的 Oil Dev Skill。这个 Skill 中包含六个 Skill，可以在开发的不同流程中使用。其中使用最多的是 Oil Plan。开发一个新功能时，我会用 Oil Plan。

它与 AI Agent 自带的 Plan 模式相比，有两个核心区别。

第一，它给出的方案更偏向业务，而且有一个很强的要求：必须让人能够读懂。AI Agent 自身的 Plan 模式有时会罗列很多与技术强相关的内容，阅读难度很高。如果不完全了解相关技术，看到方案时可能只会觉得“写得很专业，应该没问题”，但实际上很难掌控它接下来几个小时会做什么。

第二，方案写完后，Oil Plan 会自动启动一个子 Agent 对方案进行 Review，目的是让方案更加完备。有时候第一次让主 Agent 编写方案时，它没有考虑清楚，遗漏了一些业务细节。此时再让子 Agent Review，通常得到的方案都会比第一版更加完善。

我的提示词通常会这样写：“接下来要开发这个网站的后端，包括登录、收款，以及一些支付功能和付费墙设置。”

Oil Dev Skill 中还有一些 Skill，在这个项目里没有怎么使用，其中一个是 Oil Exploit。它会派发多个子 Agent 探索整个项目。不过，这个项目的功能复杂度并不高，所以我很少让它派发子 Agent 查看代码。主 Agent 看几个文件，基本就能知道这个项目是做什么的。

AI Agent 实现并完成功能后，我会让它运行一次 Oil Code Review。这个过程非常简单：Agent 会参考我的规范进行代码审查，发现问题后直接修复。

另一个非常常用的 Skill 是 Oil Governance，主要用于管理项目中的文档。项目的 Agent Stand MD 中，应写入常用且必要的内容，同时删掉已经失去作用的内容。

除此之外，我的项目中还有许多规范，例如课程写作规范、配图规范和发版规范。在每次使用 AI Agent 的过程中，只要遇到新问题，就应该及时处理。这里的新问题不一定是程序 Bug，也可能是 AI 误解了我的意思，或者某次任务没有执行到位。修复问题后，一定要要求 AI 反向优化对应的规范，这样以后就可以直接使用这个 Skill，减少自己重复输入提示词的工作量。

例如，我在写作过程中提出“段落之间的过渡衔接也要自然”，AI 完成这次修改后，还应将这一要求沉淀到写作规范中，注明后续文章也要保持行文流畅。这样，它以后就会把这条要求写进我的写作规范。

下面再说说登录和收款模块。首先，我的后端没有引入专门的登录组件或第三方登录框架，而是基于 Next.js 的后端接口和 Neon 数据库，直接实现一套轻量的方案就足够了。

目前，产品支持两种登录方式。第一种是邮箱免密登录，这需要接入外部的邮件发送服务，我使用的是 Resend，它是目前非常主流的邮件服务之一。第二种是 Google 登录。接入 Google 登录时，可以前往 Google Cloud 的凭据控制台，创建一个网页应用的 OAuth 登录授权。其中需要填写网站地址和回调地址，也就是登录后需要跳转到你网站上的哪个地址，授权才能成功。后端则使用 Google 官方提供的基础框架，这样就可以快速完成接入。

这些事情对 AI 来说都非常简单。告诉它具体要求后，它就可以自行配置。像 Google 平台的配置页面，也可以让 AI 使用浏览器自动化工具自行填写。

收款方面，我使用的是 Stripe。因为这个知识库提供了 Pro 会员，部分内容只有 Pro 会员才能阅读全文。Stripe 的优势是，只要手中有一张香港的银行卡就可以开通。我之前做的许多产品都使用过 Stripe，而且它还支持开通国内支付渠道。

接入 Stripe 非常简单。现在很多 AI 编程工具都有 Stripe 插件，例如 Codex Cloud 等。如果没有，可以安装 Stripe CLI。整个流程从创建产品到测试调试，通常很少需要人工介入。支付功能基本可以交给 AI 完成。

在这个过程中，人负责的是产品定价：采用买断制还是订阅制，售价定为多少，以及是否设置优惠券等。具体的支付功能实现则交给 AI。

还有一个重要的技术点。由于这是一个知识库网站，其中包含付费内容。例如，读者正常阅读到某一部分时，后面的内容就应该通过付费解锁。因此，后端接口不能把付费部分的原文直接响应给前端，否则任何人都可以轻易拿到内容。不能只在前端通过样式遮挡付费内容，而必须在服务端控制数据，付费内容根本不能被响应到前端。

遇到这类技术问题时，一定要让 AI 确认清楚，并从多个角度审查是否存在与业务相关的特殊数据泄露问题。

框架搭建完成后，我就可以开始向网站补充内容。最开始规划要写哪些课程时，我会让 AI 阅读我以前录制的所有视频。过去的视频都有字幕、文字稿和脚本，因此可以让 AI 分析过往内容，归纳出一批系统化的课程选题。

当时，我给 AI 的要求是：“接下来我想写一门从零到一学习 Vibe Coding 的课程，可能会分为很多章，你觉得应该怎么设计？你可以看看我以前的视频，规划一下。”这是一个非常口语化的需求。

大家可能会觉得，既然以前已经录过视频，想把内容整理成课程应该很简单：直接让 AI 将口播稿或脚本整理成课程文章，再补充一些内容就可以了。

但如果直接让 AI 整理成课程，会出现四个非常明显的问题。

第一，视频内容的有效信息密度不够。我的口播稿中有大量临场补充和介绍。一期视频可能有两三十分钟，但真正写成一篇课程后，可能只有几百字就能表达完。

第二，AI 整理出来的讲述链路与我实际讲述的链路并不一致。课程属于阅读型内容，如果让 AI 从零到一重新组织，读起来就会没那么对味，仍然需要较多人工输入，文章才会更自然，也更有人味儿。

第三，文字内容应该是视频内容的超级浓缩版本。文字的信息密度可以很高，有时几句话就能表达视频中相当多的内容。

第四，过去的视频可能存在时效性问题。比如，我在视频中介绍过一些旧模型，AI 读取这些内容后，可能会把旧模型，以及过去与现在差异很大的思考，一起写进课程。我更希望写新课程时尽可能忽略时间周期，除非某个领域确实发生了重大的技术变革。对于仍然比较通用的洞察，则可以保留。

因此，我在写新课程时采用访谈式写作，让 AI 担任采访者，围绕本次要写的主题向我提问。我通过语音输入，把当下真实采用的做法以及个人判断直接说出来，AI 再负责整理。AI 会完整记录每一轮口述的原文，一个字都不允许修改。

等全部内容聊完后，我会先查看原稿，核对 AI 记录得是否准确。确认没有问题后，再让它整理成正式章节。整理时只允许进行最小化调整，不能添油加醋。

即便如此，AI 在整理时仍不可避免地会出现一些添油加醋的情况。例如，我让它调整一个段落，它可能慢慢忘记前面提出的要求。

针对这个问题，我还编写了一个文案审查的 Lint，也就是一种自动检查脚本。我会设置一些绝对不允许出现的词。每次写完文章后，都需要运行程序检查一遍。

由于我主要使用 Claude 写作，因此它生成的大多数问题都是 Claude 常见的表达习惯。例如“很具体的痛点”“发现了几个很具体的问题”“非常直接”“原因很现实”以及一些非常生硬的过渡套话。

我自己基本不会使用这种表达方式。“发现一个很具体的问题”这种写法过于直接，而“我现在跟你说的是大白话”“我要跟你讲的通俗易懂”“我给你掰开揉碎了讲清楚”“不用强调我是用大白话跟你说的”等句子，也属于典型的生硬表达。

另外，还有一些过度拟人和夸张的修饰，以及单独使用底层、脾气、焊死等词语。这些拟人化的动词或单字动词容易让人感觉用力过猛，AI 味很重。把这些问题在文本中逐一控制好，文章读起来就会自然很多。

自己平时看文章时，只要看到“很具体”“发现了几个很具体的问题”等表达，通常就能判断这是 AI 写的。

每次完成写作后，我还会让一个单独的子 Agent 再审查一次，主要检查两个问题。

第一个问题是文章中的过渡衔接。通读全文，检查各处衔接是否自然。

第二个问题是检查上下文是否充分。站在一个不了解相关内容的读者角度，假设读者第一次接触这部分知识，看看是否在没有铺垫的情况下就直接引入了新概念。

例如，如果函数参数写得过于复杂，突然引入这类知识，那么非技术背景的读者阅读起来就会非常费劲。遇到这种情况，我需要确认如何表达才能更加清楚，或者是否应该先做一些铺垫、补充示意图，帮助读者理解这个概念。

从文章中也可以看到，课程还配有图片。图片上方或下方通常还有文字描述，因为图片有时比较抽象，经过一定的艺术加工后，既能让人感到有趣，也不会像纯文字那样枯燥。

我的文字和图片是分开处理的。现在 AI 已经能够非常稳定地生成文字，例如图片上方和下方的说明文字，大多由 AI 生成。但图片上的描述文字是让 AI 单独撰写的，而不是直接在生成图片时写入图片中。这样做也是为了提高后期编辑的灵活性。

AI 生图还可以应用在很多地方。除了网站文章中的配图，还可以生成网站图标、Logo，以及书籍封面。我的书籍封面已经更换过两版，目前这一版是我认为效果比较好的。

书籍封面同样有自己的规范。我会分别制定配图规范和封面规范，下次生成图片时，让 AI 参考这些规范。其中一个要点是，不要与现有图片重复。每次生成图片后，都要把提示词保存下来。下一次让 AI 生成时，它看到之前的提示词，就会重新构思，而不会简单重复。

不过，封面上的文字仍然由 AI 直接生图。因为封面的编辑次数不多，而且让 AI 直接生成图片，可以把文字样式处理得更加好看。

最后是如何部署上线。我的服务运行在 Vercel 上。Vercel 是目前主流的前端部署云服务平台，代码托管在 GitHub 上，再由 GitHub 连接 Vercel。每次向 GitHub 推送新代码，都会触发 Vercel 的自动部署。

在 Vercel 中，还可以配置域名。我之前介绍过，从主域名下分出了一个以 book 开头的子域名。访问这个域名时，会直接进入 Vercel 提供的服务。

这个域名是在 Cloudflare 上购买的。通常情况下，只要不是非常热门的域名，花费大约十美元、也就是七十元人民币左右就足够了。

我现在把它挂在主域名下，就不需要额外花钱了，给它添加一个前缀解析即可。这样，一个七十块钱的域名就可以供很多个网站使用。

我的网站还有一个功能，就是 Newsletter，也就是邮件订阅通知。上线新文章之后，我可以给用户发送邮件，告知他们：“我们有一门新课程上线了，如果你感兴趣，可以进来看一看。”

它的原理也很简单。我们前面使用了 Resend 服务，它可以帮助我们发送邮件，所以我可以直接在里面实现一个脚本。每当上线一门新课程后，我就让 AI 调用这个脚本，给用户发送通知。

这些用户是怎么来的呢？网站里本来就有数据表，可以通过数据表找到已经登录，并且确认接收通知的用户，然后把邮件发送给他们。

这里还有一个小技巧：邮件可以设置模板，把它设计得好看一些。这样，大家看到这个网站时，就会觉得它具有一种成熟产品的质感。

除了新博客上线、新文章上线之类的通知之外，登录验证码的模板也可以设计得好看一些。这些内容本质上都是 HTML，可以让 AI 帮忙设计，然后使用你自己的账号发送一些测试邮件，检查一下实际效果。

你看一下最终呈现的效果好不好。如果用户收到邮件时觉得：“哇，这个网站做得很成熟。”而不是只收到一串“你的验证码是巴拉巴拉巴拉巴拉”这样难看的内容，那这个设计就是有效的。
