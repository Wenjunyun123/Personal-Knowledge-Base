# FDE 一手信息源核验与 12 周学习路线

> 研究日期：2026-08-07  
> 关联笔记：`Adrian Punk- 想要找FDE工作的普通人，强烈建议去看这本书： 《前线部署工程师：人工智能时代的.md`  
> 范围：只把官方仓库、公司官方岗位/产品/工程资料、官方标准与原始文档作为事实依据。学习路线和验收阈值是基于这些材料做的工程化建议，不是任何一家公司的官方课程。

## 结论先行

FDE 不是简单的“驻场开发”或“售前技术支持”。OpenAI 当前岗位说明把它定义为端到端生产部署责任：负责 discovery、technical scoping、system design、build、production rollout，并用生产采用率、可衡量的工作流影响和 eval 驱动的反馈衡量成功。Palantir 的官方定义更短：FDSE 的使命是为客户达成技术和运营结果。

最可验证的完整链路是：

1. 定义业务结果、成功标准和初始工作流；
2. 连接系统，编码政策、权限与人工升级路径；
3. 完成安全、隐私和法务审查；
4. 运行模拟、评估和验收测试；
5. 小范围受控上线并监控结果；
6. 根据生产证据持续改进；
7. 将有效模式沉淀成工具、playbook 或可复用组件，并把现场反馈送回产品/模型路线图。

前六步直接来自 OpenAI Presence 官方部署说明，第七步来自 OpenAI FDE 当前岗位职责。它比书中“找对问题 → 赢得客户 → 激活部署 → 守住续约 → 扩大收入 → 规模化复制”更适合作为个人学习和作品集的技术主线；书的链路还包含销售、续约和扩张等商业职责，是否由 FDE 本人承担会因公司而异。

## 12 周学习 TODO

建议每周 8–12 小时，始终围绕一个真实工作流做同一项目。不要每周换 demo。优先找 1–3 位真实使用者或领域专家；没有真实用户时，明确标注为“模拟项目”。

### 第 0 周：定题与基线

- [ ] 选一个可接触用户、可获得脱敏样本、4–8 周可上线小范围试用的工作流。
- [ ] 完成 3 次用户/领域访谈，画 current-state workflow。
- [ ] 写一页 Problem Brief：用户、触发、输入、当前步骤、痛点、基线、目标、非目标、风险。
- [ ] 定义 1 个业务主指标、2 个质量护栏、延迟与成本预算。
- [ ] 验收：领域专家签字/文字确认“问题与基线基本准确”；否则不得进入开发。

### 第 1 周：FDE 角色与交付链

- [ ] 阅读 OpenAI FDE JD、Presence、Palantir FDSE 定义。
- [ ] 把项目拆成 discovery → scope → design → build → acceptance → rollout → improve → reuse。
- [ ] 建 Decision Log，记录范围/速度/质量取舍。
- [ ] 验收：能用 5 分钟讲清“为什么它是运营结果项目，不只是 AI demo”。

### 第 2 周：技术范围与业务语义

- [ ] 列出系统、数据源、业务对象、关系、动作、角色与权限。
- [ ] 画架构图和数据流图；标出 PII/机密数据边界。
- [ ] 定义人工审批、拒绝执行和升级路径。
- [ ] 验收：每个动作都有 owner、授权条件、失败处理和审计记录。

### 第 3 周：最小端到端切片

- [ ] 用 Python + TypeScript/JavaScript（或同等栈）打通 UI → API → 模型 → 工具/数据 → 结果。
- [ ] 使用结构化输出并校验 schema；实现超时和可理解错误信息。
- [ ] 建单元测试与一个端到端 happy-path 测试。
- [ ] 验收：用脱敏真实样本完整跑通一个工作流；不是只展示聊天回答。

### 第 4 周：情境化 Evals

- [ ] 与领域专家定义“好”的 rubric 和不可接受错误。
- [ ] 建代表性评估集：常见任务、边缘案例、拒答/越权、脏数据和工具失败。
- [ ] 固化 baseline，比较至少两种 prompt/模型/工作流方案。
- [ ] 验收：所有关键失败可复现；上线门槛在测试前书面约定，不事后挑数字。

### 第 5 周：检索、工具与系统集成

- [ ] 只在确有依据时加入 RAG；记录引用与来源权限。
- [ ] 工具调用实现最小权限、参数校验、幂等和 dry-run/确认机制。
- [ ] 模拟超时、限流、错误响应、数据缺失。
- [ ] 验收：无权限用户无法获得或修改受限数据；失败不会静默产生错误业务动作。

### 第 6 周：安全、隐私与治理

- [ ] 按 NIST AI 600-1 做轻量风险登记：风险、概率、影响、控制、owner、残余风险。
- [ ] 做威胁模型：prompt injection、数据泄露、越权工具、供应链、日志泄密。
- [ ] 检查密钥、PII 脱敏、留存、审计、删除流程和依赖漏洞。
- [ ] 验收：高风险动作必须人工确认；测试日志不含密钥或未脱敏敏感数据。

### 第 7 周：生产可靠性

- [ ] 加 trace/log/指标：成功率、质量、延迟、成本、工具错误、人工升级率。
- [ ] 实现重试边界、熔断/降级、版本化配置、灰度与回滚。
- [ ] 做一次故障演练并写 Runbook。
- [ ] 验收：能在限定时间内发现失败、定位一次请求、回滚到上一稳定版本。

### 第 8 周：受控试点与采用

- [ ] 让 3–5 位目标用户完成真实或安全沙箱任务。
- [ ] 记录完成率、耗时、错误、求助点和信任问题；访谈“不使用”的原因。
- [ ] 更新培训、空状态、错误提示和人工接管体验。
- [ ] 验收：使用者能在无开发者代操作时完成目标任务；采用数据与业务结果均可见。

### 第 9 周：价值验证

- [ ] 对照第 0 周基线测量时间、质量、成本或风险变化。
- [ ] 区分已测结果、用户自报、外推估算和未知项。
- [ ] 写继续/修改/停止建议及证据。
- [ ] 验收：不能只报模型准确率；必须至少有一个工作流结果指标和一个风险护栏。

### 第 10 周：产品化与复用

- [ ] 把客户特定逻辑与通用能力分层。
- [ ] 抽取可复用 connector、eval、schema、guardrail、部署模板和 playbook。
- [ ] 用第二组相似数据/工作流验证复用，记录仍需定制的部分。
- [ ] 验收：新场景复用步骤可由另一名工程师照文档完成；不能把复制粘贴称为平台化。

### 第 11 周：交接与运营

- [ ] 完成 README、架构、数据字典、权限矩阵、Runbook、评估报告、发布/回滚说明。
- [ ] 和未来 owner 做一次交接演练。
- [ ] 建 backlog：现场问题、产品改进、模型反馈分开记录。
- [ ] 验收：原作者离线时，owner 能部署、观察、处理常见故障并回滚。

### 第 12 周：作品集与面试防守

- [ ] 写案例：Context → Discovery → Decisions → Build → Evals → Rollout → Outcome → Reuse → Limits。
- [ ] 准备 10 分钟 demo、5 分钟技术深挖、5 分钟业务价值说明。
- [ ] 练习回答失败、范围取舍、客户冲突、安全事故、未达到目标和后续计划。
- [ ] 验收：所有结果都有可展示证据；把个人练习、模拟用户、真实试点、生产使用清楚分开。

## 作品集项目统一验收清单

- [ ] **问题证据**：访谈纪要、流程图、基线、明确 owner 与非目标。
- [ ] **端到端价值**：真实/脱敏样本从输入走到业务动作，而非孤立聊天界面。
- [ ] **评估证据**：版本化 eval 集、rubric、baseline、回归结果和失败分类。
- [ ] **工程质量**：自动测试、类型/schema 校验、错误处理、可维护代码。
- [ ] **生产控制**：权限、审计、人工升级、监控、灰度、回滚、Runbook。
- [ ] **使用证据**：目标用户独立完成任务；记录采用、反馈和不采用原因。
- [ ] **结果证据**：至少一个工作流指标 + 一个质量/风险护栏；口径和限制透明。
- [ ] **复用证据**：至少一个组件/playbook 在第二场景验证；明确仍需定制处。
- [ ] **交接证据**：另一人可按文档运行和排障。
- [ ] **诚信边界**：练习、模拟、试点、生产、个人贡献与团队成果分别标注。

## 对原书的使用建议

把书当作“案例地图与问题清单”，不要把所有数字直接当结论。最可靠的使用方式是：先读章节形成假设，再到附录 C 找出处，最后回到来源所有者的官方页面、原始论文或公司披露核验。附录 C 自己已经提醒部分材料属于媒体转引、第三方估算、单一来源、综合叙述或匿名案例；这些内容适合启发追问，不适合在简历和面试中说成已确认事实。
