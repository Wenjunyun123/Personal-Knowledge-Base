# 谷歌开发者大会收获：HyperFrames 渲染管线优化笔记

**作者：**小天fotos

**时长：**约 7.4 分钟

**一句话概括：**受 Chrome 的 HTML in Canvas 能力启发，作者重编译浏览器相关代码并改造渲染管线，把同一份 4K 60 帧素材的离线渲染时间从 73 分 37 秒压到 14 分 15 秒，提升约 5.17 倍。

## 一、背景：剪辑流程已全面转向 HyperFrames

作者的视频剪辑方式已经整体改变，现在全面转向 HyperFrames。工作方式上，AI 会理解素材、转写人声、找到每个字词的时间戳，并自动安排画面、字幕和动画。

过去是在剪映的时间轴上一个一个手动拖镜头；现在更像是给 AI 一份「导演稿」，由它把素材准备好，并执行整条片子。

![[笔记同步助手/images/949d25e1bf8a6d6caf4d6788757d3d0d_MD5.jpg|作者说明剪辑流程从手工拖时间轴转为向 AI 提供导演稿]]

作者说明剪辑流程从手工拖时间轴转为向 AI 提供导演稿

## 二、HyperFrames 是什么

可以把它理解成「用网页来做视频」：

-   **HTML** 负责内容；
-   **CSS** 负责画面；
-   **JavaScript 和 GSAP** 负责动画。GSAP 是一条可编程的动画时间轴，你告诉它每个元素从哪里来、何时出现、怎么移动，它就能在任意时间点准确还原状态。

再配合字词时间轴，画面就能在讲到某个词的时候同步强调关键词、数字和逻辑关系。它比 PPT 更连贯，也比普通字幕更有表达力。

## 三、痛点：渲染太慢

HyperFrames 有一个让人很痛苦的问题：渲染实在太慢。它采用了一种很笨的办法。

一分钟的 4K 60 帧视频，就是 3600 张画面。传统流程是：

1.  让浏览器跳到一个时间点；
2.  完成布局和绘制；
3.  把画面截成 PNG 或 JPEG，导出浏览器；
4.  再交给 FFmpeg 编码。

动画本身可能并不复杂，但 CPU 却一直在压图片、复制数据、搬运像素。

![[笔记同步助手/images/31fd19dcf3f256277161d36430029a27_MD5.jpg|讲解 HyperFrames 逐帧截图渲染流程导致 CPU 负载过高]]

## 四、谷歌开发者大会的线索：HTML in Canvas

作者受邀参加谷歌开发者大会，在做功课时发现 Chrome 正在推进一项叫 **HTML in Canvas** 的能力。

Canvas 原本就擅长画图片和图形，HTML/CSS 则由另外一套网页排版系统负责。HTML in Canvas 做的事情，是让 Canvas 直接看到一棵已经排版好的 HTML 树：DOM 先照常算出文字的位置、样式和层级，再把内部的绘制记录直接序列化进入 Canvas。

![[笔记同步助手/images/9a2c9c7e73fa09e4276fde3d31f032dd_MD5.jpg|Chrome 推进 HTML in Canvas 能力的介绍画面]]

它不是用 JavaScript 重新模仿一遍网页，所以更接近浏览器真正画出来的结果。进入 Canvas 之后，它还能变成 WebGL 纹理去做 3D 或特效。

![[笔记同步助手/images/3a1bf78425e18efed40bfee78dbd9937_MD5.jpg|DOM 绘制记录序列化进入 Canvas 的流程示意]]

HyperFrames 现在已经支持了这条实验路径，打开对应 flag 就能用。它不再通过传统的整页截图接口，而是直接复用 DOM 的绘制结果。

![[笔记同步助手/images/bddee499404d18a9a37c9e55394709f4_MD5.jpg|HyperFrames 开启 flag 后启用实验渲染路径]]

**效果：**原本 70 分钟左右的渲染，一度降到了 40 分钟。

![[笔记同步助手/images/f076644eb83d6c9ba2a83c6889505c46_MD5.jpg|渲染时间从 70 分钟降至 40 分钟的数据展示]]

## 五、HTML in Canvas 的局限

它并不是万能的截图方案，限制不少：

-   内容必须进入 Canvas 树；
-   跨域内容会因安全限制被排除；
-   视频、复杂滤镜、混合模式、3D 变换和嵌套内容都有可能会丢失，或者回退到旧的「一张一张截图」路径；
-   高分辨率的 DPR 放大和多 worker 并行也有限制；
-   更关键的是，它只缩短了「HTML 到 Canvas」这一段，浏览器仍然要逐帧布局、绘制并等待 paint，后面还有可能把 Canvas 压成图片、跨进程传输再交给编码器，CPU 依然会很忙。

所以，从 70 分钟降到 40 分钟是很大的进步，但对作者来说依然不可用——40 分钟也没办法等。

![[笔记同步助手/images/3492f9aa0995821117b97125028277f7_MD5.jpg|列举 HTML in Canvas 的各类限制与回退路径]]

## 六、思路转折：录屏为什么快

作者想到：同一个网页直接播放并录屏，几乎可以实时完成。为什么离线渲染反而这么慢？

原因是录屏能从浏览器合成后的 GPU 画面里直接取帧，不必让每一帧都变成一张图再搬来搬去。

![[笔记同步助手/images/8e1e2357769a19901f092a0cbf4af3d6_MD5.jpg|对比录屏取帧与离线逐帧截图的差异]]

对比录屏取帧与离线逐帧截图的差异

带着这个问题，作者去谷歌开发者大会找了相关开发人员。对方给出的答案并不让人满意：「如果你现在就想要，那你就改代码吧。」

于是回来之后，作者真的把 Chrome 相关代码重新编译了一遍，用大白话说，做了四件事。

## 七、四项核心改造

### 改造一：不再给每一帧「打包寄快递」

旧流程先把几千万像素压进 PNG 或 JPEG，送到另一个进程再拆开使用。现在 Canvas 画完，直接把它标记成一帧视频交给编码器，包装、拆包和来回复制都省了。

![[笔记同步助手/images/c9bd368e80b9a90aa8f95edcc10ebe30_MD5.jpg|改造一：Canvas 输出直接作为视频帧交给编码器]]

改造一：Canvas 输出直接作为视频帧交给编码器

### 改造二：不再让视频播放时「猜」帧

以前把进度拖到第 10 秒，浏览器给出的可能是 10 秒附近的画面。现在先给素材做一本精确到帧的目录，需要哪一帧就取哪一帧；同一个素材、同一个时刻出现两次，也只解码一次。

### 改造三：放开 Intel 硬件编码的 30 帧限制

让它支持 4K 60 帧，并把 Canvas 画面整理成 Intel 编码器能直接接收的格式。CPU 不再一张一张压 H.264，而是负责调度和限速，真正的编码交给硬件。

![[笔记同步助手/images/dc19e809a5c8a761748cc22b3e3b0308_MD5.jpg|改造三：放开硬件编码帧率限制，CPU 转为调度角色]]

改造三：放开硬件编码帧率限制，CPU 转为调度角色

### 改造四：给整条流水线装上「限速器」和「质检」

前面的环节不能无限产生数据把内存塞爆；视频帧和音频必须严丝合缝，只有帧数、时长、颜色和声音全部正确，临时文件才能变成最终的 MOV。

## 八、测试数据

-   **编译机：**线程撕裂者 5995WX，256G 内存；
-   **实际运行机器：**i7-13620H、32G 内存、Intel 核显的小主机；
-   **测试素材：**4K 60 帧，共 40,382 帧；
-   **原始 HyperFrames：**73 分 37 秒；
-   **改造后：**14 分 15 秒；
-   **提升：**约 5.17 倍。

## 九、当前边界与开源计划

Intel 核显同样有边界。目前跑通的是普通的 H.264 视频，而 H.264 不保存 Alpha 透明层，所以还不能直接交付透明背景的动画，也无法把它导进剪映当素材。透明格式（例如 ProRes 4444）还需要另外一条管线，作者还没有做。

接下来作者准备把这条线路开源，仓库会提供锁定的版本、补丁、构建脚本、benchmark、验收工具以及 ASQ。如果要使用，需要准备 80～100G 的空间来编译这个特定版本的 Chrome。

## 十、方案本身的风险

-   能渲染出来，不一定等于画面一定正确；
-   复杂动画、WebGL 以及嵌套页面，有时在抓帧时会丢失状态；
-   分辨率和缩放处理不一致，也可能导致画面只占左上角之类的异常。

因此，正式渲染前必须先测动态样片；渲染完成后也必须抽帧检查，不能只看命令显示成功。而且即使不算渲染本身，也还有准备时间，说明这套方案目前还达不到真正「一键完成渲染」的程度。

## 十一、更大的启发

作者认为这件事最大的收获，是意识到身边很多看似必须靠更强硬件才能解决的低效，可能并不是机器不够快，而是软件没有把每个环节优化到位。推理引擎不断在提升速度，就是同样的道理。

AI 时代真正赋予个人的能力是：只要把问题想清楚、问得足够具体，就能和 AI 一层一层追到源码，把过去只有专业团队才能做的优化做出来。这些优化，作者一行代码都没写，全部由 AI 完成。

![[笔记同步助手/images/b9c6fe69cb53bd15b5b9c77cc532772f_MD5.jpg|作者总结软件优化比升级硬件更值得优先考虑的启发]]

作者总结软件优化比升级硬件更值得优先考虑的启发

所以，作者想买顶配 Mac 的念头也没那么强了。升级硬件当然省事，但在花钱之前也许应该先问一句：

> 现在的性能，究竟是被算力限制，还是被软件浪费了？

多研究一点软件和管线，省下的也许不只是时间，还有一大笔硬件钱。

## 全文整理

朋友们，如果最近看过我的视频，可能已经发现我的剪辑方式全都变了。现在我的视频里已经全面转向 HyperFrames，AI 会理解素材、转写人声，找到每个字词的时间戳，再自动安排画面、字幕和动画。以前是我在时间轴上、在剪映里一个一个地拖镜头；现在更像是我给 AI 一份导演稿，它把素材也准备好，在整条片子里执行出来。

本期是一个管线优化的经验分享，但我也得稍微说一下 HyperFrames 到底是个什么。可以把它理解成用网页来做视频，但各司其职：HTML 负责内容，CSS 负责画面，JavaScript 和 GSAP 负责动画。GSAP 就是一条可编程的动画时间轴，你告诉它每个元素从哪里来、何时出现、怎么移动，它就能在任意时间点准确还原状态。再配合字词时间轴，画面就能在某个字词出现的时候同步强调关键词、数字和逻辑关系。它比 PPT 连续，也比普通字幕更有表达力。

但 HyperFrames 有一个让我很痛苦的问题，就是渲染真是太慢了。它用了一种很笨的办法：一分钟 4K 60 帧的视频就是三千六百张画面。传统流程要等浏览器跳到一个时间点，完成布局和绘制，再把画面截成 PNG 或 JPEG 导出，浏览器再交给 FFmpeg 编码。动画可能并不复杂，但 CPU 却一直在压图片、复制数据、搬运像素。

前段时间我受邀参加 Google 开发者大会。我做功课的时候发现，Chrome 正在推进一项叫 HTML in Canvas 的能力。Canvas 原本就擅长画图片和图形，HTML、CSS 则由另外一套网页排版系统负责。HTML in Canvas 做的就是让 Canvas 直接看到一棵已经排版好的 HTML 树。浏览器先照常算出文字的位置、样式和层级，再把内部的绘制记录直接序列化进入 Canvas。它不是用 JavaScript 重新模仿一遍网页，所以更接近浏览器真正画出的结果。进了 Canvas 之后，它还能变成 WebGL 纹理去做 3D 或者特效。听不懂也没关系。HyperFrames 现在已经支持了这条实验路径，打开这个 flag 就能用了。它已经不再通过传统的整页截图接口，而是直接复用 DOM 的绘制结果。我原本七十分钟左右的渲染一度降到了四十分钟。

但它不是万能截图。内容必须还是得进入 Canvas 树，跨域的内容还会因为安全限制被排除。视频、复杂的滤镜、混合模式、3D 变换和嵌套内容都有可能丢失，或者回退到旧的路径，也就是一张一张截图。高分辨率的 DPR 放大和多 worker 并行也有限制。更关键的是，它只缩短了 HTML 到 Canvas 这一段。浏览器仍然要逐帧布局、绘制并等待 paint，后面还有可能把 Canvas 压成图片、跨进程传输再交给编码器，所以 CPU 依然会很忙。从七十分钟降到四十分钟是很大的进步，但对我来说依然不可用，四十分钟也没办法等。

这时候我就想到：同一个网页直接播放再录屏，几乎是可以实时完成了。那为什么离线渲染反而这么慢？因为录屏能从浏览器合成后的 GPU 画面里直接取帧，不必让每一帧都变成一张图再来回搬运。所以我就带着这个问题去 Google 开发者大会找他们的开发人员。他给我的答案我并不满意，他说如果你现在就想要，那你就改代码吧。于是回来我就真的把 Chrome 代码和 Electron 都重新编译了一遍。

用真正的大白话说，我做了四件事。

第一，不再给每一帧打包寄快递。旧流程先把几千万像素压进 PNG 或 JPEG，送到另一个进程，再拆开使用。现在 Canvas 画完，我直接把它标记成一帧视频交给编码器，包装、拆包和来回复制都省了。

第二，我不再让视频播放的时候猜这帧了。以前你把进度拖到第十秒，浏览器可能给你的是十秒附近的画面。我先给素材做了一本精确到帧的目录，需要哪一帧就取哪一帧。同一个素材、同一个时刻出现两次，也只解码一次。

第三，我放开了对 Intel 硬件编码三十帧的限制，让它支持 4K 60 帧，并把画面整理成 Intel 编码器能直接接收的格式。CPU 就不再一张一张压 H.264 了，而是负责调度，核显负责真正的编码。

第四，给整条流水线装上了限速器和质检。前面不能无限产生、把内存塞爆。视频帧和音频必须严丝合缝，只有帧数、时长、颜色和声音全部正确，临时文件才能变成最终的 MOV。

我的编译机是一台线程撕裂者 5945WX，有 256G 内存。但实际我运行它，只需要用一台 i7-13620H、32G 内存、Intel 核显的小主机。不知道能不能看到。我测试的是 4K 60 帧，总共四万零三百八十二帧。原始的 HyperFrames 需要用七十三分钟三十七秒，改造后是十四分十五秒，提升约五点一七倍。其实我也不懂，都是 AI 搞的。

Intel 核显也有边界。我现在跑通的是普通的 H.264 视频，而 H.264 不保存 Alpha 透明层，所以还不能直接交付一个透明背景的动画，也就是不能把它导到剪映里当素材。透明的比如 ProRes 4444 等格式，还需要另外一条管线，这我还没做。

我准备把管线开源了，仓库会提供锁定的版本、补丁和构建脚本、benchmark、验收工具，还有 ASQ。如果你要用，得准备八十到一百 G 的空间来编译这个 Chrome 的特定版本。

但这个方案其实也有一些限制。它现在最大的问题是，能渲染出来不一定等于画面一定正确。比如复杂动画、WebGL 还有嵌套页面，有时候在抓帧的时候就会丢失状态；分辨率和缩放处理不一致，也可能导致画面只占左上角这种诸如此类的问题。所以正式渲染前必须先测动态样片，渲染完成后也必须抽帧检查，不能只是看命令显示成功。所以其实如果不算它的渲染，它也有一些准备的时间。它并不能说现在直接就是一键完成渲染，还没有达到这种程度。
