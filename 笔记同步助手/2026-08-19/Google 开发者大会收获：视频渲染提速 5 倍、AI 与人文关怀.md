## 三、第一块拼图：HTML in Canvas — 视频渲染提速 5 倍

### 3.1 HTML in Canvas 是什么

以前浏览器里有两个互不相通的世界：HTML 负责排版，Canvas 负责高性能绘图。HTML in Canvas 把真实的 HTML 元素划进 GPU 加速的 Canvas 中，两个世界由此打通。

舞台演示了一个 3D 小房间：房间里的网页用 HTML 写，却能随意旋转透视，文字照样可以选中、搜索，甚至能实时翻译。该能力已在 Chrome 148 中开放试用。

![[笔记同步助手/images/20a4d172c0bac8887427f3536a6743c0_MD5.jpg|3D 小房间中 HTML 网页可旋转透视的演示]]

3D 小房间中 HTML 网页可旋转透视的演示

### 3.2 与创作者工作的结合点

创作者视频里的 Lottie / Luma / Motion Graphics 动画都是用 Hyperframe 这个 AI Agent 工具制作的。但它渲染一直很慢：每秒钟 60 帧不停地截图，一分钟就是 3600 张。一条 10 分钟视频往往要等一两个小时。

Hyperframe 最近悄悄上线了一个实验性功能——用 HTML in Canvas 的方式渲染。Canvas 是 GPU 加速的输出，过去那些不卡的高性能动画都来自 GPU；现在 HTML 也能放到 Canvas 里渲染，速度自然就上来了。

### 3.3 自己的优化过程

去大会之前，光是这一步，10 分钟的 4K 视频渲染时间从 70 分钟降到了 40 分钟。但创作者不甘心，去展台问 Google 工程师能否更快。得到的答案是：Chrome 难以为这种小场景改底层，不过它是开源的，可以直接走 GPU。

回来后重新捋了一遍渲染管线，砍掉了三条弯路：

-   画好的帧不再保存成图片再读回来，直接交给显卡
-   压缩素材不再等动画播到才现取，改成按帧号点播——要哪帧给哪帧
-   Chrome 源码硬编码的 30 帧直接改成 60 帧

4K 60 帧才真正上了快车道：去展会前还要跑 40 分钟的渲染，现在 14 分钟跑完，**和最初相比整整快了 5 倍**。整套方案稍后会开源。

## 四、第二块拼图：Web MCP — 让 Agent 直接操作网页

现在的 Agent 想操作网页非常费劲：先截图、再读 DOM、再解析无障碍数据、再把几条信息揉在一起猜。页面只要变化，整套逻辑就得重来一遍，token 哗哗地烧。

Web MCP 是 Google 和微软一起推进的开放标准。网页主动把自己的能力（一次搜索、一个表单、一个按钮）声明成结构化的工具，Agent 不用看网页，直接调用就行。

创作者当晚回去就做了个 demo：用语音 Agent 通过 Web MCP 操作界面，用语音下指令，Agent 调用网页声明的工具，界面实时反馈。

### 5.3 withA11y：让视障者「读」到图片

NVDA 是 20 年前由视障者发起的开源屏幕阅读软件；中国也有一个完全由志愿者组成的中文社区。withA11y 是社区里一位视障开发者用业余时间为社区写的开源软件。

中国有 1700 万视障者。普通读屏软件虽然能读出标题和文字，但遇到图片时他们听到的往往只有两个字：「图片」。打开 withA11y 之后，Gemma 4 e4b 的多模态能力会把每一张图细细读出来——而且不止读出来，还要理解上下文：同一个垃圾桶图标出现在应用按钮里和出现在垃圾分类文章里，读法是不一样的；默认描述不够时使用者还可以继续追问。

北邮有位视障学生学计算机，最头疼的是数学公式：普通文字可以直接朗读，图片里的公式却几乎没法读。现在 withA11y 能把公式转译成读屏软件可以逐项读取的代码。

## 六、回顾与反思

创作者平时做科技内容，眼睛总盯着最新模型和 coding agent 的性能。这次才发现，真正让人愿意停下来的，是这些最朴素的应用——它们有文化的分量，也有社会的分量。

前沿的模型在比谁跑得快，但这些项目在回答另一个问题：技术是为了谁？

> 技术的终点不是参数，而是每个人都能用得起、用得好。

## 七、本次收获总结

-   **更快的渲染速度**：视频渲染提速 5 倍（10 分钟视频从 70 分钟 → 14 分钟）
-   **能操作网页的 Agent**：Web MCP 的语音控制 demo
-   **无数被激发的灵感**：HTML in Canvas 的更多玩法、Gemma 4 多模态模型
-   **最重要的认知**：产品里应该有的人文关怀

篇幅有限，更多技术细节可以在评论区提问。

## 全文整理

前几天参加了 Google 开发者大会，收获不小。我带着问题去，带着答案回来。照着现场学到的东西，我把 AI 视频渲染流程提速了五倍，而这只是第一块拼图，我还有更大的收获。这次视频很长，建议先收藏，慢慢看。先谢谢抖音科技和 Google 的邀请，让我有机会来到 2026 年 Google 开发者大会。说实话，这是我第一次参加，来的那天上海台风刚走，我早上七点多撑着伞去世博中心踩点。门口的 IO Connect 装置已经被加固得严严实实，本来以为自己到得够早，没想到 Google 比我起得还早。

八点多的创作者欢迎会上，Google 大中华区首席市场官黄建忠过来打招呼。他说了一句我记到现在的话：五月的 IO 在美国是发布，到了八月的中国，最大的不一样是 "我们"，他们更想让人看到的是中国开发者怎么用这些技术。他还叮嘱我们：看到好的开发者案例，记得讲给更多人听。那这期视频就算我交的作业。

开场的 keynote 就让我有点意外。Google 在自己的舞台上，主角几乎全是中国企业。vivo 把 Google Cloud 的 TPU 当做出海的算力底座，还有智能眼镜上的主动式 AI 翻译，延迟压得很低。在 Google 的主场看到这些中国企业出海的实践，说实话挺提气的。Google 还宣布，继厦门和深圳之后，广州和杭州的跨境电商加速中心今年第三季度也投入运营，这是要一路陪着中国开发者出海。

今年大会的主题叫做 "智体心境"。台上有一句话几乎替我总结了这两年的工作方式：写 prompt 只是热身，Agent 的执行才是正赛。开发者不再逐行写代码，而是管理一群 agent。这句话说完，我在台下想了想：这不就是我每天的日子吗。说回到我自己，我是提前做了功课的，这次大会的几个模块对我的工作效率意义重大。我来就是想从 Google 的技术栈里找几块能真正落地的拼图。所以 keynote 一结束，我就直奔第一个目标。

### 第一块拼图：HTML in Canvas

第一个目标是 HTML in Canvas。花三十秒先讲讲它是什么。以前浏览器里有两个互不相通的世界：HTML 负责排版，Canvas 负责高性能绘图。HTML in Canvas 做的事就是把真实的 HTML 元素划进 GPU 加速的 Canvas 里，两个世界就从此打通了。舞台上演示的是一个 3D 小房间，房间里的网页是 HTML 写的，但它能随意旋转、透视，文字照样能选中、能搜索、甚至能实时翻译。这个能力已经在 Chrome 148 里开放试用了。

展台我也特意去了一趟，找工程师当面确认。以前想在幕 Canvas 里放动态内容，得用 JavaScript 一帧一帧绘制上屏，而且文字还不好看。现在可以把动态元素直接注入进去，而且它本质上还是 HTML，搜索、翻译这些能力全都在。对很多人来说这是个新特性，但对于我来说那是实打实的生产力。

常看我视频的朋友知道，我的视频里类和 overlay 动画都是 AI agent 用 Hyper Frame 这个工具做的。但它渲染起来一直很慢，因为用的办法很笨：不停地给动画截图，每秒六十帧，一分钟就是三千六百兆。渲染一条十分钟的视频，往往要等到一两个小时。

Hyper Frame 最近悄悄上线了一个实验性功能，就是用 HTML in Canvas 的方式渲染。原理不复杂：Canvas 是 GPU 加速的输出。你见过那些不卡的粒子动画对吧，那都是 GPU 的功能。现在 HTML 也能放到 Canvas 里渲染了，速度自然就上来了。

去大会之前我就做过实验，光是这一步，我一条十分钟的 4K 视频渲染时间就从七十分钟降到了四十分钟。快是快了，但是我不甘心，又去展台拉住了 Google 的工程师，问能不能更快。他说 Chrome 很难为我这个小场景去改底层，不过它是开源的，你可以直接走 GPU。这句话直接就点醒了我：HTML 渲染不再绕道截图，直接读 GPU，那我的流水线是不是也在绕路呢？

回来之后，我把整条渲染管线重新捋了一遍，砍掉了三条弯路。画好的帧不再保存成图片再读回来，直接交给显卡压缩；素材也不再等动画播到才现取，而是改成了按帧号点播，要哪帧给哪帧。Chrome 源码硬编码的三十帧我直接改成六十，4K 六十帧才真正上了快车道。整个渲染优化完，从去展会前还跑四十分钟到现在十四分钟跑完，和最初比整整快了五倍。所以这一趟真的是值得。

当然整套方案我稍后都会开源，等我们后续的视频吧。Google 的创新帮到了我，我也想让它接着帮到更多的人。

### 第二块拼图：Web MCP

那第二站是 Web MCP。它解决了什么问题？展台的工程师讲得很直白：它不是后端 API，而是给已经在网页里的 agent 用的。现在的 agent 想要操作一个网页其实很费劲：先截一张图，再读 DOM，再解析无障碍树，再把几条信息揉在一起猜。页面只要一变化，整套逻辑就得重来一遍，token 哗哗地烧。

Web MCP 是 Google 和微软一起推进的开放标准。网页主动把自己的能力（一次搜索、一个表单、一个按钮）声明成结构化的工具，agent 就不用太费劲看网页了，直接调用就行。我当晚回去就做了个 demo，让语音 agent 通过 Web MCP 操作界面：用语音下指令，agent 调用网页声明的工具，界面实时反馈。第二块拼图就到位了。

### 第三块拼图：AI for Social Good

第三站与其说是技术，不如说是大会里的一个环节：AI for Social Good。Keynote 里有一句话我当时一度以为是场面话——"科技向善在中国的开发者手中已经从宏伟的愿望变成一个个生动的现实"。

这里的每个项目都建立在 Google 的开放模型上。最大尺寸的 Gemma 4 31B，能跑在端侧的 E4B，还有专门理解自然声音的 Perch。快速认识一下 Gemma 4 这一代开放模型：从端侧的 E 系列到 31B，原生支持多步规划和函数调用，视频、图片、音频都能理解，协议是宽松的 Apache 2.0。Gemma 4 的累计下载量已经突破了三亿次。

主旨演讲还分享了语音 AI 智能体 Q 的案例：他把默认文字润色引擎换成本地的 Gemma 4 E4B 之后，该环节的处理延迟降低了百分之四十四，编辑服务成本降至零。他放的 demo 就是让 agent 离线运行帮他改代码。

在 AI for Social Good 的舞台上，这些开放技术换了一副样子。央美的青年艺术家做了一件剪纸：你在屏幕上画一道弧线，剪纸里的生肖就跃然纸上。旁边那件唐俑的作品更直接：你穿什么颜色，屏幕里的唐俑就换成什么色调；你在屏幕前转身，它也跟着转。北大的团队把录音设备放进山里，用刚刚提到的 Perch 来听懂鸟鸣，一个物种只有七个样本它也能学会。华南理工的师生用 Gemma 4 12B 在本地搭起了教学平台，让 AI 站上讲台当助教。

说实话，站在剪纸和唐俑面前我有点诧异。拆开看，剪纸的那些"秘密"都是 Gemma 4 的多模态能力加一段写得很好的系统提示词，模型看着你画给你建议。没有微调，没有管线，谈不上什么工程，可围在那里的人是我那天看到最多的。我平时做科技内容，眼睛总是盯着最新的模型、coding agent 的性能，那天我才发现真正让人愿意停下来的，是这些最朴素的应用。它们有文化的分量，也有社会的分量。

那一刻我有点明白 Google 为什么把 AI for Social Good 单独做成一个板块。前几个模型在比谁跑得快，但这些项目在回答技术是为了谁。

不过整个展区让我停了最久的是另一个项目，它和前面的案例都不太一样。NVDA 是二十年前由视障者发起的开源屏幕阅读软件，中国也有一个完全由志愿者组成的 NVDA 中文社区。WithAware 就是社区里一位视障开发者用业余时间为这个社区写的开源软件。中国有一千七百万视障者，读屏软件虽然可以把标题和文字读出来，但是遇到图片，他们听到的往往只有两个字：图片。

打开 WithAware 之后，Gemma 4 E4B 的多模态能力就会把每一张图细细读出来。它比把图读出来多做了一步——理解上下文。比如同一个垃圾桶图标，出现在应用按钮里和出现在垃圾分类的文章里，读法是不一样的。默认描述不够用的时候，使用者还可以接着追问。

北邮就有位视障学生学计算机，他最头疼的就是数学公式。普通文字可以直接朗读，图片里的公式却几乎没法读。现在 WithAware 能把公式转译成读屏软件可以逐项读取的代码。

演讲最后那位开发者说：用身边的技术解决生活里的一个小问题，让科技真正服务到每一个人，这就是他长期做开源的快乐来源。他说过一句话：被忽略的不只是图片，更是我们与这个世界的联系。我们几秒钟就划走一条视频，图片多到看不过来，而看不见的人想要的只是一张图片被认真地读出来——一个能在本地跑、有耐心把一张普通图片细细讲给他们听的小模型，让他们能更真切地知道，原来我们都生活在同一个世界。

而这几个 AI for Social Good 展区讲的是同一件事：哪怕 AI 再强大，也可以俯下身来，变成每个普通人伸手就能握住的力量。台上反复说的那些理念，在这里就有了现实的样子。技术的终点不是参数，而是每一个人都用得起、用得好。
