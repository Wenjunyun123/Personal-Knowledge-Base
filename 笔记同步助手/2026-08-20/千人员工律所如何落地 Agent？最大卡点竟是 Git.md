## 一、背景：一家千人员工律所的 Agent 落地

本期节目聊的是 Anthropic 介绍的一家美国律所——ABC Legal，规模约 1000 人，看他们如何用 Claude Managed Agents 把公司内部的本地 Agent 搬上云。

Key Context：Claude Managed Agents 本质上还是一个 API，从 API 到真正可落地的产品之间，存在巨大 gap。这也是当下很多企业最普遍的痛点——拿到了 Agent 能力，但不知道怎么落地。

## 二、上云之前：本地 Agent 是一个黑盒

年初龙虾（Cursor 类似的本地 AI 编程工具）很火的时候，ABC Legal 内部很多员工自发地用本地 Agent 搭了一些工具，装在自己电脑上，帮自己处理零碎的工作。这些 Agent 全部跑在员工个人电脑里。

这种模式对企业来说有三个核心问题：

-   **不可见**：每个 Agent 每天调用多少次、花了多少钱、效果怎么样，企业完全看不到，是一个黑盒。
-   **不可控**：企业对这些 Agent 没办法掌控。
-   **资产流失**：员工作为 Agent 的创造者，一旦离职，电脑格式化，所有积累的 AI 技能、Skill、Prompt、MD 文档全部随之消失。

![[笔记同步助手/images/b9bc380b92f3043710443880b072e84f_MD5.jpg|本地 Agent 模式的三个核心问题示意图：不可见、不可控、资产流失]]

本地 Agent 模式的三个核心问题示意图：不可见、不可控、资产流失

这里引出一个重要观点：**Skill、Prompt、MD 文档正在取代代码，成为企业最宝贵的资产**。以前我们写代码是写资产，现在员工编写的 Skill、Prompt、Markdown 文档同样是半结构化文档形态的资产，并且可能比代码更重要——因为人走了，"数字员工"可以留下来。

![[笔记同步助手/images/4d6cc018f1945554e316ef5370b9dd85_MD5.jpg|Skill、Prompt、MD 文档成为企业新资产的概念图]]

## 三、第一步：把本地 Agent 搬上云

ABC Legal 的第一个动作是**上云**——把所有的本地 Agent 集中到云端运行。上云之后带来的好处是：

-   每个 Agent 每天推理了多少次、花了多少钱，企业可以清楚看到；
-   可以做版本控制；
-   可以不断进行优化迭代；
-   相当于把分散的资产集中管理起来了。

![[笔记同步助手/images/721b5b429df6f894b7e58d682786893c_MD5.jpg|本地 Agent 集中上云后的管理视图]]

## 四、怎么落地：让业务部门自己的人来构建 Agent

第二个动作是**怎么在不同的部门落地**。ABC Legal 的核心理念是：企业构建 Agent 不能都通过技术部门。

如果所有部门构建 Agent 都通过技术部门，技术部门就成为瓶颈、成为堵塞。Agent 的构建需要由最懂业务的人来做——也就是各业务部门的人。

### 具体做法：每个部门抽调 1-2 人

从每一个业务部门里抽调 1-2 个人，总共十几个人组成一个小组，先给他们培训，教他们怎么用 Claude Managed Agents API 去搭一个 Agent 出来。先把这十几个人教会，他们学会了之后，再回到自己的部门里去教其他人。

![[笔记同步助手/images/223884cb2c7eea3bd7d2f1687312dc02_MD5.jpg|每个部门抽调 1-2 人组成小组的培训模式示意图]]

每个部门抽调 1-2 人组成小组的培训模式示意图

### 给非技术人员的工具形态

让业务部门的人直接使用 Claude Managed API 其实门槛还是不低（定义 Agent、定义环境、起 Session 等）。所以 ABC Legal 内部应该有一个研发部门，做了一个 Agent Builder——通过对话的方式来搭建 Agent。

可能的形态有两种：

-   **界面式**：把 API 包装成一个 UI 界面对非技术人员最友好；
-   **CLI 包装式**：把几个原子能力包装成 CLI，提供给 Builder，Builder 通过自己本地的 Agent（比如 Claude Code）调这些 CLI，去创建一个自己想要的云端 Agent。

![[笔记同步助手/images/fc9b3be391242d7d388c0b84ea97aa75_MD5.jpg|Agent Builder 产品形态：UI 界面与 CLI 包装两种方式对比]]

## 五、最大卡点：Git

在这个落地过程中，ABC Legal 发现：造 Agent 本身并不是什么大的卡点，对普通人来说，通过跟 Agent 对话的方式写一些东西、搭一个简单的 Agent 出来并不费劲。

但是！**遇到的最大的卡点是 Git**。

因为他们的 Agent 都是在 Git 上面管理的（有版本概念，会不断对 Skill、Prompt、工具进行迭代）。所以他们把 Agent 的代码、Skill、Context 全部放在 Git 仓库上管理。但是普通人要参与到 Agent 的构建当中，他需要理解 Git 的概念、理解这一套协作的方法（PR、Commit、Push），这对普通人来说是最大的卡点。

![[笔记同步助手/images/f5e70946204ade8c3dbfc07af031f90d_MD5.jpg|Agent 资产在 Git 上管理的示意图：Skill、Prompt、Context 文件]]

Agent 资产在 Git 上管理的示意图：Skill、Prompt、Context 文件

### 为什么 Git 是绕不开的？

企业最终要的是：员工离职后，他平时工作的那些技能、能力（Skill、Prompt、MD 文档）能像代码一样沉淀在 Git 仓库里。以后新员工基于这个仓库起一个 Agent 实例，这个"数字员工"就还可以继续留在这里。

所以培训的重点就是：教普通人怎么用 Git 提 PR、提 Commit，理解这一套协作流程。

![[笔记同步助手/images/acfc8bc13bae3a984171b6240ba44234_MD5.jpg|普通人使用 Git 协作的门槛示意图：PR、Commit、Push 流程]]

普通人使用 Git 协作的门槛示意图：PR、Commit、Push 流程

### 一个值得出现的产品机会

这里有一个产品机会：能不能在 Git 上面再包一层应用层，把 PR、Commit 这些东西做得更产品化？

之前的 Git 是面向程序员的，但如果是面向普通人的版本管理工具，可能可以做得比 Git 更好。底层可能还是 Git，只是在中间包一层更面向普通人的应用产品层。以后可能就会出现这样的产品，让更多的人去用上 Agent 的东西。

![[笔记同步助手/images/41ea49857c5618dee0bcf5963a939708_MD5.jpg|在 Git 之上包一层面向普通人的应用层的产品构想]]

## 六、效果：搭了几十个法律 Agent

ABC Legal 用 Claude Managed Agents API 在公司里搭了几十个 Agent，全部是去做各种法律相关的工作。落地效果应该还是挺好的。

![[笔记同步助手/images/6c72a60a0283bd24736838360cddda3f_MD5.jpg|ABC Legal 内部搭建的几十个法律相关 Agent 列表]]

ABC Legal 内部搭建的几十个法律相关 Agent 列表

这里的关键洞察：**以后企业跑在本地或云端的 Agent，对企业的重要性不亚于代码**。其实比代码还重要——因为代码是显性的，但企业里那些口口相传的经验，如果能通过 Skill、Prompt、Markdown 文档沉淀下来，对企业才是最宝贵的。

## 七、为什么 Agent 落地在广东比北京更快？

观察到一个现象：广东（特别是深圳）那边的 AI 落地或 FDE，比北京这边走得更靠前。

原因有几个：

-   **企业属性差异**：北京这边央国企比较多，作为一个个人 FDE 或去对接央国企，难度很大，因为你需要走很多合规流程；但广东那边很多都是私人老板。
-   **老板更关心效果**：广东的私人老板更愿意去拥抱 AI，他关心的是方案效果怎么样——比如原来要花几百万成本的事情，你二十万就能通过 AI 改造，而且是以持续迭代的方式去做，能帮他节省成本、改善效果，他们就会要这个东西。

## 八、FDE 角色的重新定义：从驻场工程师到 AI 布道师

两个月前的主观感受：FDE 就像是"上一个时代的驻场工程师"。

经过这两个月，感觉有改观——FDE 不仅仅是驻场工程师，**他更多的是一个 AI 工程师**，要打通 Agent 落地的最后一公里。

![[笔记同步助手/images/0d194a153bf8127d936100676223a036_MD5.jpg|FDE 角色演进：从驻场工程师到 AI 布道师/AI 工程师]]

FDE 角色演进：从驻场工程师到 AI 布道师/AI 工程师

### FDE 需要的三种核心能力

真正的 Agent 落地，FDE 需要的能力远不止"带 Claude 进去让员工用一下提效"。还需要：

1.  **懂技术，能对接企业 IT 系统**：大企业有老的 IT 系统、ERP 流程，这些是数据源。要把这些数据源接上 Agent，给它接上手和工具。
2.  **清楚告诉 Agent 目标是什么**：要让 Agent 干掉什么事情，目标的定义要清晰。
3.  **解决 Context 获取问题**：Agent 有一个聪明的脑子，但得给它接上手——能获取多少 Context 决定它能干多少事。比如通过 ERP 系统拿指定权限的数据源，做加工处理、生成报表。

![[笔记同步助手/images/940ac550fa6fa6f291b3520b74f548cc_MD5.jpg|FDE 三种核心能力：技术对接、目标定义、Context 获取]]

FDE 三种核心能力：技术对接、目标定义、Context 获取

## 九、未来的一个方向：Agent 资产的备份系统

一个判断：**Agent 必须在云端**。无论是对监控、效果迭代还是别的方面，云端都比本地更可控。老板可以看用量、看你干活的产出。

但同时，云端 + 本地**两者并存**可能更合理：

-   员工自己的 Agent 可以跑在电脑上（可以减少云端成本，只需要给员工配对应的 API Key，员工自己也会自发去买一些推理 API Key）；
-   员工沉淀的 Skill、Markdown 文件、Context 信息，需要有一个系统能一键备份到云端仓库。

这个系统就像是 Agent 版的"代码云端备份"——上一个时代，你本地的代码能备份到云端；对于现在大家都是 Agent 操盘手的人来说，你核心资产就是 Skill、Prompt、那些文档，你也应该有一个上传到云端的共享系统。

这样它就能作为企业的核心资产，进行后续的迭代和下一任员工的迭代学习。

![[笔记同步助手/images/bfb915ed6b722444924385cb43520a4d_MD5.jpg|Agent 资产备份系统：从本地沉淀一键备份到云端共享仓库]]

Agent 资产备份系统：从本地沉淀一键备份到云端共享仓库

## 十、总结：五条核心洞察

1.  **本地 Agent 是黑盒**：企业不可见、不可控、资产随人走。Skill、Prompt、MD 文档正在取代代码，成为企业最宝贵的资产。
2.  **上云是第一步**：把分散在员工电脑里的 Agent 集中上云，才能实现可视化、可控、可迭代。
3.  **落地靠业务部门**：每个部门抽调 1-2 人组成小组，先培训学会，再回去教同事，避免技术部门成为瓶颈。
4.  **最大卡点是 Git**：普通人不懂 PR、Commit、Push 这套协作流程。需要在 Git 之上做一层面向普通人的产品层，这是一个值得出现的产品机会。
5.  **FDE 是 AI 布道师**：不是上个时代的驻场工程师，而是要打通最后一公里的 AI 工程师——懂技术、懂业务、懂 Context 对接。
