## 一、HyperFrames 的基本思路

HyperFrames 是一种用网页技术制作视频的方式：HTML 负责内容结构，CSS 负责画面呈现，JavaScript 与 GSAP 负责动画控制。GSAP 可以被理解为一条可编程的动画时间轴，用来精确描述每个元素在什么时间出现、从哪里来、如何移动，以及在任意时间点应当处于什么状态。

在这种流程中，AI 会理解素材和转写人声，找到每个字词对应的时间戳，并自动安排画面、字幕与动画。相比手动在剪辑软件时间线上拖动镜头，这更像是给 AI 一份导演稿，由它准备素材并执行整条片子。

![[笔记同步助手/images/1f21d9e4ff19c7b589735c3e01fb2d98_MD5.jpg|视频开头介绍 HyperFrames 工作方式]]

视频开头介绍 HyperFrames 工作方式

这种方式比 PPT 更连续，也比普通字幕更有表达力。它能够在说到某个关键词、数字或逻辑关系时，同步强调对应的文字和画面元素。

## 二、原始渲染流程的问题：太慢

HyperFrames 早期最大的问题是渲染速度很慢。以一分钟 4K、60 帧视频为例，需要输出 3600 张画面。传统流程通常是让浏览器跳到某个时间点，完成布局和绘制，再把画面截图成 PNG 或 JPEG，导出浏览器后交给 FFmpeg 编码。

这个流程的瓶颈不一定在动画本身，而在大量图片压缩、数据复制与像素搬运。即使动画并不复杂，CPU 仍然会持续处理截图、压图、跨进程传输和编码任务。

## 三、HTML in Canvas 带来的实验路径

作者在参加 Google 开发者大会前做功课时，注意到 Chrome 正在推进一项名为 HTML in Canvas 的能力。Canvas 原本擅长绘制图片和图形，而 HTML 与 CSS 通常由浏览器的网页排版系统处理。HTML in Canvas 的目标，是让 Canvas 能直接看到已经排版好的 HTML 子树。

其大致流程是：浏览器先照常计算文字位置、样式和层级，再将内部绘制记录序列化进入 Canvas。它不是用 JavaScript 重新模拟网页，因此更接近浏览器真实绘制出的结果。进入 Canvas 后，内容还可以变成 WebGL 纹理，用于 3D 或特效处理。

![[笔记同步助手/images/87f8f237026b4a1cd8571151b56c527d_MD5.jpg|介绍 Chrome HTML in Canvas 能力的画面]]

介绍 Chrome HTML in Canvas 能力的画面

HyperFrames 已经支持这条实验路径。开启相关 flag 后，它可以不再通过传统整页截图接口，而是直接复用 DOM 的绘制结果。作者原本约 70 分钟的渲染，一度降到约 40 分钟。

### HTML in Canvas 的限制

-   内容仍必须进入 Canvas 可处理的绘制路径。
-   跨域内容可能因为安全限制被排除。
-   视频、复杂滤镜、混合模式、3D 变换以及部分嵌套内容，可能丢失或回退到旧的逐帧截图路径。
-   高分辨率 DPR 放大和多 worker 并行也存在限制。
-   它主要缩短 HTML 到 Canvas 的环节，浏览器仍然需要逐帧布局、绘制并等待 paint。

因此，从 70 分钟降到 40 分钟已经是明显进步，但对作者的实际生产来说仍然不够快。

## 四、进一步思路：为什么播放录屏很快，离线渲染却很慢

作者观察到，同一个网页直接播放并录屏时，几乎可以实时完成。原因是录屏可以从浏览器合成后的 GPU 画面中直接取帧，不必让每一帧先变成图片，再进行反复搬运。

带着这个问题，作者在 Google 开发者大会上询问相关开发人员。得到的建议是，如果现在就想实现这种能力，就需要自己改代码。随后作者重新编译了 Chrome 代码和 Electron，并围绕渲染管线做了改造。

## 五、作者做的四项管线优化

### 1\. 不再把每一帧打包成图片再传递

旧流程会先把几千万像素压进 PNG 或 JPEG，送到另一个进程后再拆开使用。改造后，Canvas 画完后直接被标记成一帧视频并交给编码器，省掉了图片包装、拆包和来回复制。

### 2\. 为视频素材建立精确帧目录

过去将播放进度拖到第 10 秒时，浏览器可能返回的是 10 秒附近的画面。作者为素材建立了精确帧目录，需要哪一帧就取哪一帧；同一个素材在同一个时刻出现两次，也只解码一次。

![[笔记同步助手/images/dee0b459a3aa28d53e23c560ab0db456_MD5.jpg|讲解精确取帧和素材帧目录的画面]]

讲解精确取帧和素材帧目录的画面

### 3\. 放开 Intel 硬件编码限制

作者放开了 Intel 硬件编码的 30 帧限制，使其支持 4K 60 帧，并将 Canvas 画面整理成 Intel 编码器能够直接接收的格式。这样 CPU 不再逐张压缩 H.264，而主要负责调度，真正的视频编码交给 Intel 核显完成。

### 4\. 给流水线加入限速器和质检

为了避免前端无限产生数据导致内存被塞爆，管线加入了限速控制。同时，视频帧和音频必须严格对齐，只有帧数、时长、颜色和声音全部正确，临时文件才会变成最终 MOV。

## 六、性能结果：约 5.17 倍提升

作者的编译机是 Threadripper 5945WX，配有 256GB 内存。但实际运行测试时，使用的是一台 i7-13620H、32GB 内存、Intel 核显的小主机。

测试任务为 4K 60 帧，总计 40382 帧。原始 HyperFrames 渲染需要 73 分 37 秒，改造后用时 14 分 15 秒，提升约 5.17 倍。

## 七、当前边界与尚未完成的部分

Intel 核显方案目前跑通的是普通 H.264 视频。H.264 不保存 alpha 透明层，因此还不能直接交付透明背景动画，也不能直接导入剪映作为带透明通道的素材使用。

如果要支持透明视频，例如 ProRes 4444 等格式，还需要另一条管线。作者表示这部分目前还没有完成。

![[笔记同步助手/images/0c50432a8956dd61c2ed5a7dc22b7cd9_MD5.jpg|说明 H.264 不支持透明通道与 ProRes 4444 需求的画面]]

## 八、开源计划与使用条件

作者准备将这条优化线路开源。仓库计划提供锁定版本、补丁、构建脚本、benchmark、验收工具以及 FAQ。使用者需要准备约 80GB 到 100GB 的空间，用于编译特定版本的 Chrome。

这套方案还不是完整的一键渲染工具。正式渲染前需要先测试动态样片，渲染完成后也必须抽帧检查，不能只看命令行显示成功。

### 仍需重点检查的问题

-   复杂动画、WebGL 或嵌套页面在抓帧时可能丢失状态。
-   分辨率和缩放处理不一致时，画面可能只占左上角。
-   能渲染出来不等于画面一定正确。
-   除了实际渲染耗时，前期准备和验证也需要时间。

## 九、核心启发：先判断瓶颈来自算力还是软件浪费

作者认为，这次优化最大的启发是：很多看似必须依赖更强硬件解决的问题，可能并不是机器不够快，而是软件没有把每个环节优化到位。

在 AI 时代，个人只要把问题想清楚、问得足够具体，就可以借助 AI 一层一层追到源码，做出过去可能只有专业团队才能完成的优化。升级硬件当然省事，但在花钱之前，也应该先判断当前性能究竟受限于算力，还是被低效软件管线浪费了。

## 全文整理

朋友们，如果你最近看过我的视频，可能已经发现我的剪辑方式完全变了。现在，我的视频已经全面转向 HyperFrames：AI 会理解素材和转写文本，找到每个字词对应的时间戳，再自动安排画面、字幕和动画。以前是我在时间轴上、在剪映里一个镜头一个镜头地拖；现在更像是我给 AI 一份导演稿，它把素材也准备好，并把整条片子执行出来。

本期内容是一个比较实用的管线优化经验分享。不过在进入正题之前，我需要先简单说明 HyperFrames 到底是什么。你可以把它理解成“用网页来做视频”：HTML 负责内容，CSS 负责画面，JavaScript 和 GSAP 负责动画。GSAP 本质上是一条可编程的动画时间轴，你告诉它每个元素从哪里来、什么时候出现、如何移动，它就能在任意时间点准确还原状态。再配合字词级时间轴，画面就能在我说到某个词的时候，同步强调关键词、数字和逻辑关系。它比 PPT 更连续，也比普通字幕更有表达力。

但 HyperFrames 有一个让我很痛苦的问题：渲染真的太慢了。它原本采用的是一种很笨的办法。以一分钟 4K 60 帧的视频为例，总共就是 3600 张画面。传统流程是让浏览器跳到某一个时间点，完成布局和绘制，再把画面截成 PNG 或 JPEG 导出浏览器，随后交给 FFmpeg 编码。动画本身可能并不复杂，但 CPU 一直在压图片、复制数据、搬运像素。

### HTML in Canvas 的实验路径

前段时间，我受邀参加 Google 开发者大会。做功课的时候，我发现 Chrome 正在推进一项叫 HTML in Canvas 的能力。Canvas 原本就擅长画图片和图形，HTML、CSS 则由另一套网页排版系统负责。HTML in Canvas 做的事情，是让 Canvas 直接看到一棵已经排版好的 HTML 子树。Chrome 先照常计算文字的位置、样式和层级，再把内部的绘制记录直接栅格化进入 Canvas。它不是用 JavaScript 重新模仿一遍网页，所以更接近浏览器真正画出的结果。

进入 Canvas 之后，它还可以变成 WebGL 纹理，用来做 3D 或特效。听不懂也没关系，重点是 HyperFrames 现在已经支持了这条实验路径，只要打开对应的 flag 就能使用。它不再通过传统的整页截图接口，而是直接复用 DOM 的绘制结果。

这条路径让我的渲染时间一度从 70 分钟左右降到了 40 分钟。但它并不是万能截图。内容必须进入可被捕获的子树，跨域内容还会因为安全限制被排除。视频、复杂滤镜、混合模式、3D 变换以及嵌套内容，都有可能丢失，或者回退到旧路径，也就是一张一张截图的路径。高分辨率 DPR 放大和多 worker 并行也有限制。

更关键的是，它只缩短了 HTML 到 Canvas 这一段。浏览器仍然要逐帧布局、绘制，并等待 paint。后面还有可能把 Canvas 压成图片，跨进程传输，再交给编码器，所以 CPU 依然会很忙。从 70 分钟降到 40 分钟已经是很大的进步，但对我来说依然不可用，40 分钟也没办法等。

### 为什么录屏更快

这时我想到：同一个网页如果直接播放再录屏，几乎可以实时完成，为什么离线渲染反而这么慢？原因是录屏可以从浏览器合成后的 GPU 画面里直接取帧，不必让每一帧都变成一张图，再来回搬运。

我带着这个问题去 Google 开发者大会找相关开发人员交流。他给了我一个答案，但我并不满意。他说，如果我现在就想要这个能力，那就改代码。于是回来之后，我真的把 Chrome 代码和 Electron 都重新编译了一遍。

用真正的大白话说，我做了四件事。

第一，不再给每一帧“打包寄快递”。旧流程会先把几千万像素压进 PNG 或 JPEG，送到另一个进程，再拆开使用。现在 Canvas 画完之后，我直接把它标记成一帧视频交给编码器，包装、拆包和来回复制都省掉了。

第二，不再让视频播放时“猜这一帧”。以前把进度拖到第 10 秒，浏览器给你的可能是 10 秒附近的画面。我先给素材做了一本精确的帧目录，需要哪一帧就取哪一帧。同一个素材在同一个时刻出现两次，也只解码一次。

第三，放开对 Intel 硬件编码 30 帧的限制，让它支持 4K 60 帧，并把 Canvas 画面整理成 Intel 编码器能够直接接收的格式。这样 CPU 就不再一张一张地压 H.264，而是负责调度，核显负责真正的编码。

第四，给整条流水线装上限速器和质检机制。前面不能无限产生数据，把内存塞爆；视频帧和音频必须严丝合缝。只有帧数、时长、颜色和声音全部正确，临时文件才能变成最终的 MOV。

### 测试结果

我的编译机是一台线程撕裂者 5945WX，配有 256GB 内存。但实际运行时，我只需要一台 i7-13620H、32GB 内存、Intel 核显的小主机。

我测试的是 4K 60 帧，总共 40382 帧。原始 HyperFrames 需要 73 分 37 秒，改造后需要 14 分 15 秒，提升约 5.17 倍。其实我也不懂，都是 AI 做的。

当然，Intel 核显也有边界。我现在跑通的是普通 H.264 视频，而 H.264 不保存 Alpha 透明层，所以还不能直接交付一个透明背景动画，也就是不能直接导入剪映当素材使用。透明格式，比如 ProRes 4444，还需要另外一条管线，这部分我还没有做。

我准备把这条线路开源。仓库会提供锁定版本、补丁、构建脚本、benchmark、验收工具以及 FAQ。如果你要使用，需要准备 80GB 到 100GB 的空间，用来编译 Chrome 的特定版本。

### 现阶段的限制

这个方案仍然有一些限制。现在最大的问题是：能渲染出来，不一定等于画面一定正确。比如复杂动画、WebGL、嵌套页面，有时候在抓帧时会丢失状态；分辨率和缩放处理不一致，也可能导致画面只占左上角等问题。

所以正式渲染前，必须先测试动态样片；渲染完成后，也必须抽帧检查，不能只看命令显示成功。严格来说，如果不计算渲染本身，它也有一些准备时间，所以还不能说现在已经达到一键完成渲染的程度。

但这件事带给我的最大收获，或者说更大的启发，是我们身边很多看起来必须通过更强硬件解决的低效问题，可能并不是机器不够快，而是软件没有把每个环节优化到位。推理引擎不也是这样吗？它们也在不断提升速度。

AI 时代真正赋予个人的能力，是只要你把问题想清楚、问得具体，就能和 AI 一层一层追到源码，把过去只有专业团队能做的优化做出来。这些优化我一行代码都没写，全是 AI 做的。

所以我现在想买 M4 Max 99 的念头也没那么强了。升级硬件当然省事，但花钱之前，也许应该先问一下：当前性能究竟是被算力限制，还是被软件浪费了？多研究一点软件和管线，省下的也许不只是时间，还有一大笔硬件钱。

今天就分享到这里。听不听得懂没关系，把这个 repo 丢给你的 AI 就可以优化了。这就是我在 Google 开发者大会交的作业，你们还满意吗？够不够干货？我们下次见。
